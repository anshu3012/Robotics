1. Overview

Key point

Carrying the cup from the table to the door takes steps in a fixed order (go to the table, pick up the cup, go to the door, put it down), not one route. We write the world as true-or-false facts and each action as the facts it needs, makes true and makes false; the task then becomes a search over sets of facts, which the graph searches of the earlier Notes already know how to do.

The robot can already plan a route. On the room’s occupancy gridOccupancy grid: A grid map that stores in each cell a number between 0 and 1, such as the probability that the cell is occupied, instead of a hard 0 or 1; the standard grid map of robotics, since sensors are never sure. Explained in: Maps and Landmarks, §5.2 Bitmaps and occupancy grids of 0.5 m cells, breadth-first search ()Breadth-first search (BFS): A search whose frontier is a queue, so it expands vertices in rings of equal moves from the start; the first route it finds has the fewest moves, which is the shortest only when every move costs the same. Explained in: Graphs and Uninformed Search, §5. Breadth-first search: ring by ring takes it from its start cell to the cell just inside the door in 8 moves of 0.5 m, 4.0 m in all. With diagonal moves, Dijkstra’s algorithm ()Dijkstra’s algorithm: A search that always settles the vertex with the smallest distance from the start found so far, which is then final, and offers each of its neighbours the route through it, keeping the shorter; with every edge cost at least 0 it finds the shortest route to every vertex (3.414 m to the door on the room grid with diagonals). Explained in: Dijkstra’s Algorithm and Priority Queues, §3.2 The algorithm: settle the nearest, update its neighbours and A* ()A search:* Dijkstra’s algorithm with the open list sorted by f=g+h, the cost so far plus a heuristic guess of the cost left; with a consistent heuristic it returns the shortest route while expanding far fewer states (9 cells against 54 on the room grid). Explained in: A* and Heuristics, §4.5 The algorithm find the shortest route, 3.414 m. The robot stands at (2 m, 1 m), on the corner of its start cell.

Now give the robot a task (Figure 1): a cup stands on the table; carry it to the door. Route search fails on this task in two ways:

  • its search state ()Search state: What a search keeps for each vertex: the quantities that decide which moves are allowed and what they cost, and nothing more, such as (cell, charge left) for a robot with a battery; leaving one out breaks the Markov property and can hide routes. Explained in: Graphs and Uninformed Search, §10. Choosing the search state: the Markov rule, what the search keeps for each place it reaches, is one of the 76 free cells, so it records where the robot is and nothing about the cup or the robot’s hand;
  • the task needs steps in a fixed order: go to the table, pick up the cup, go to the door, put it down. The shortest route to the door, 3.414 m, leaves the cup behind.

Figure 1: The room of the chapter, 7 m by 4 m, with the table, the cabinet and the two poles. The robot stands at (2, 1) facing 30 degrees; a cup stands on the table near its left edge. Three places are marked with dashed green circles: start (the robot’s spot), table (beside the table, where the robot can reach the cup) and door (just inside the doorway). On the right, the eight facts of the task, with the three true at the start in black: robot-at start, cup-at table, hand-empty. The goal is cup-at door

So the robot needs two things: a way to write down where things are and what it holds, and a way to write down what each step changes. Choosing a sequence of steps from a description of the world in true-or-false statements is symbolic task planning ()Symbolic task planning: Choosing a sequence of actions that reaches a goal, from a description of the world in true-or-false facts such as “the cup is on the table”; it decides the order of steps (go to the table, pick up, go to the door, put down) that a route search alone cannot. Explained in §1. Overview. (P&M §6.1; LaValle §2.4). “Symbolic” because the planner reasons with names, such as “the cup is on the table”, not with coordinates in metres.

The planner works with three places, marked in Figure 1:

  • start, where the robot stands now: the start cell (x 2.0 to 2.5 m, y 1.0 to 1.5 m);
  • table, the cell beside the table’s left edge (x 2.5 to 3.0 m, y 1.5 to 2.0 m), where the robot can reach the cup;
  • door, the goal cell of route search, just inside the doorway (x 3.5 to 4.0 m, y 3.5 to 4.0 m).

Going from one place to another is one step for the planner; the route search of the earlier Notes drives it (Section 5.3). In this Note we build the planner for the cup task:

  • facts and states, and why we never list every state (Section 2);
  • STRIPS actions, with their precondition, add list and delete list, and the frame problem they avoid (Section 3);
  • PDDL, the standard way to write a task down for any planner (Section 4);
  • forward search, which finds the plan on a graph of states, first breadth-first and then with A* (Section 5).

2. Describing the task with facts

Key point

The first gap of route search is that a cell says nothing about the cup. We fix it with eight true-or-false facts about the robot, the cup and the hand; a state is the set of facts true now, and the start state holds robot-at start, cup-at table and hand-empty.

2.1 Facts and states

A grid cell says nothing about the cup, so we list the statements about the task that can be true or false. Such a statement is a fact ()Fact (task planning): A statement about the task that is either true or false, such as robot-at table or holding-cup; facts are what a planner’s states, actions and goals are made of. Explained in §2.1 Facts and states. (P&M §6.1; LaValle §2.4.1). The cup task needs eight facts:

  • robot-at start, robot-at table, robot-at door: where the robot is;
  • cup-at start, cup-at table, cup-at door: where the cup is lying;
  • holding-cup: the robot holds the cup;
  • hand-empty: the robot holds nothing.

The list on the right of Figure 1 marks the facts that are true at the start. The set of facts that are true at one moment is a state ()State (task planning): The set of facts that are true at one moment, every other fact being false, such as {robot-at start, cup-at table, hand-empty}; it records the objects and the robot’s hand, which a grid cell cannot. Explained in §2.1 Facts and states. of the task; every fact not in the set is false. The start state, which we name S0, holds three facts:

  • robot-at start;
  • cup-at table;
  • hand-empty.

hand-empty looks redundant, since holding-cup being false says the same. hand-empty is needed because a STRIPS precondition lists only facts that must be true, never facts that must be false (FAU AI-1 notes §8.4), so “the hand is empty” must be a fact of its own; the Blocks World domain, a standard planning example, uses arm-empty the same way (UMBC PDDL notes).

The task asks for one fact: cup-at door. The set of facts that must all be true at the end is the goal of the task (P&M §6.2). The goal says nothing about where the robot ends up, so every state that holds cup-at door meets it: with the robot at the start, at the table or at the door (LaValle §2.4.1: a goal stands for a set of states).

A sequence of actions that turns the start state into a state that meets the goal is a plan (P&M §6.2). For the cup task a person sees one at once:

  1. move from the start to the table;
  2. pick up the cup;
  3. move from the table to the door;
  4. put the cup down.

A computer does not see the plan. The computer must be able to tell, for any state, which actions it can take and where they lead. The next question is how many states it might have to consider.

2.2 Why we never list every state

A computer could list every state with the result of every action in it. Each fact is true or false on its own, so every new fact doubles the number of possible sets of facts. Figure 2 grows the true-or-false choices for the three robot-at facts, one fact per frame. Watch each level split every set in two: 1 set, then 2, 4 and 8. In the frame “only 3 of the 8 sets can happen”, only {start}, {table} and {door} stay, because the robot is always in exactly one place.

Figure 2: A tree of true-or-false choices, one fact per frame. Frame ‘no fact decided yet’: 1 set. Frames for robot-at start, robot-at table and robot-at door: each set splits into a true branch (green) and a false branch (red), giving 2, 4 and 8 sets; the 8 leaves list the places where robot-at is true, from {start, table, door} to {}. Frame ‘only 3 of the 8 sets can happen’: {start}, {table} and {door} turn blue, the other 5 are crossed out. Last frame: the count table on the right reaches 8 facts and 256 sets

With all eight facts, eight twos are multiplied:

2×2=4 2×2×2=8 28=256

The same in symbols:

  • n is the number of facts, 8 for the cup task;
  • N is the number of possible sets of facts.
N=2n =28=256

Most of the 256 sets can never happen, such as a robot at the start and at the door at once. From the start state only 12 can (notebook): the robot in one of 3 places, and the cup in one of 4 spots (on the table, in the hand, at the start, at the door):

3×4=12

Even so, a table that lists every state with the result of every action in it, such as “in S0, moving to the table gives S1”, is a poor way to describe a task, for three reasons (P&M §6.1.1):

  1. Too many states. A fourth place adds two facts, one robot-at and one cup-at, so the 8 facts become 10 and the number of possible sets grows from 256 to 1024.
  2. One change rewrites everything. Adding a battery level to the task changes every state in the table.
  3. The pattern is hidden. Moving from the start to the table changes only where the robot is, in every state where the move is possible, but a table of states cannot say so.

Reason 1 in numbers, with 10 facts:

210=1024

The third reason is the way out: describe each action once, by the few facts it changes, and let the computer build the states when it needs them.

3. STRIPS actions

Key point

The second need of the Overview, a way to write down what each step changes, is met by describing each action once by three lists of facts: its precondition (what must be true to do it), its add list (what it makes true) and its delete list (what it makes false). Every fact on neither list keeps its value; in the state S1, pick-up table removes cup-at table and hand-empty, adds holding-cup and leaves the other five facts alone.

3.1 Precondition, add list and delete list

Section 2.2 left us needing a description of each action by the few facts it changes. Take picking up the cup at the table:

  • before it, three facts must be true: the robot is at the table, the cup is on the table, the hand is empty;
  • after it, one fact has become true: the robot holds the cup;
  • and two facts have become false: the cup is no longer on the table, and the hand is no longer empty.

These three lists are how the STRIPS planner describes an action (P&M §6.1.2; LaValle §2.4.1). STRIPS, the STanford Research Institute Problem Solver, was the planner of Shakey, one of the first robots built with artificial intelligence (P&M §6.1.2). The three lists are:

  • the precondition ()Precondition: The facts that must be true for an action to be done, such as robot-at table, cup-at table and hand-empty for picking up the cup; the planner tries an action only in states that hold all of them. Explained in §3.1 Precondition, add list and delete list.: the facts that must be true for the action to be done;
  • the add list ()Add list: The facts an action makes true, such as holding-cup for picking up the cup; applying the action puts them into the state. Explained in §3.1 Precondition, add list and delete list.: the facts the action makes true;
  • the delete list ()Delete list: The facts an action makes false, such as cup-at table and hand-empty for picking up the cup; applying the action takes them out of the state. Explained in §3.1 Precondition, add list and delete list.: the facts the action makes false.

An action described by these three lists is a STRIPS action ()STRIPS action: An action described by three lists of facts, its precondition, add list and delete list, as in the STRIPS planner of the Shakey robot; one such description replaces a table of the action’s result in every state. Explained in §3.1 Precondition, add list and delete list.. The four actions of the plan of Section 2.1:

ActionPreconditionAdd listDelete list
move start tablerobot-at startrobot-at tablerobot-at start
pick-up tablerobot-at table, cup-at table, hand-emptyholding-cupcup-at table, hand-empty
move table doorrobot-at tablerobot-at doorrobot-at table
put-down doorrobot-at door, holding-cupcup-at door, hand-emptyholding-cup

A move deletes the old place because the robot cannot be in two places at once. The other actions of the task are the same three kinds at the other places (notebook):

  • a move from each of the 3 places to each of the other 2;
  • a pick-up at each of the 3 places;
  • a put-down at each of the 3 places.
3×2=6 moves 6+3+3=12 actions

The 12 actions describe the whole task. What they are for is applying them to a state, which Section 3.2 does.

3.2 Applying an action

With the three lists, the computer can now check the plan of Section 2.1 by itself, one action at a time. An action can be done in a state only when every fact of its precondition is true there; the action is then applicable in that state (P&M §6.2). Doing it takes the delete list out of the state and puts the add list in (P&M §6.1.2; LaValle §2.4.1). Our example is pick-up table in the state S1, the state after move start table:

  • s is the state before the action, a set of facts; here S1, which holds robot-at table, cup-at table and hand-empty;
  • pre is the action’s precondition: robot-at table, cup-at table, hand-empty;
  • del is its delete list: cup-at table, hand-empty;
  • add is its add list: holding-cup;
  • s′ is the state after the action;
  • ⊆ means “every fact on the left is also on the right”: the set {robot-at table} ⊆ S1 is true, while {holding-cup} ⊆ S1 is false;
  • ∖ means “take out”: S1 ∖ del keeps the facts of S1 that are not in del;
  • ∪ is the union ()Union (A ∪ B): The set of elements in A or B (or both), such as the points inside either of two convex pieces of an obstacle; for events, the event that A or B (or both) happens. Explained in: Naive Bayes Foundations: Mutually Exclusive Events, §5. The addition rule: where mutual exclusivity pays off of two sets: every fact that is in either one.

The test for applying the action, and the next state:

pre⊆s s′=(s∖del)∪add

On S1, the three facts of the precondition are all in S1, so pick-up table is applicable. Taking out the delete list leaves one fact:

s∖del={robot-at table}

Putting in the add list gives the next state. We call it S3, because Section 5.1 numbers the states in the order its search makes them:

s′={robot-at table,holding-cup}

The order of the two steps does not matter here, because no fact is on both lists of an action.

Figure 3 applies the whole plan this way, one action at a time. Watch the fact list on the right. In each frame named “is its precondition true?”, the needed facts turn blue. In the next frame, named “delete list removed, add list added”, the deleted facts turn red and the added ones green, while the room on the left shows the robot and the cup where the facts now say they are. The last frame, “goal reached”, holds cup-at door, so the plan meets the goal.

Left: the room, with the robot driving each move along a shortest route of grid cells (orange trail) and the cup (orange dot) on the table, then in the robot’s hand, then at the door. Checking a plan we were given takes four applications of the rule. Two questions are still open: why describe actions by their changes at all (Section 3.3), and how a computer finds a plan that nobody gave it (Section 5).

3.3 Why lists of changes: the frame problem

Section 3.2 changed only 3 of the 8 facts with pick-up table; the other 5 stayed as they were. Writing down what every fact is after the action needs a line for each of the 8 facts, and 5 of those 8 lines only say “stays the same”. Figure 4 puts the two descriptions of pick-up table side by side: on the left, the full list, with five grey lines that say “stays”; on the right, the STRIPS lists, with only the three coloured changes.

Figure 4: The action pick-up table, done in the state S1, described two ways. Left, ‘every fact, after the action’: eight lines; robot-at start, robot-at table, robot-at door, cup-at start and cup-at door are grey and say ‘stays false’ or ‘stays true’; cup-at table and hand-empty are red, ‘becomes false’; holding-cup is green, ‘becomes true’. Right, ‘STRIPS: only the changes’: precondition robot-at table, cup-at table, hand-empty; add holding-cup; delete cup-at table, hand-empty; every other fact keeps its value. Below: over all 12 actions, 12 times 8 = 96 lines on the left, 66 of them ‘stays the same’; STRIPS writes 30 list entries and leaves the 66 out

Over all 12 actions of the task:

  • A is the number of actions, 12;
  • n is the number of facts, 8;
  • c is the number of changes, counted over all actions: 2 for each move (one fact added, one deleted), 3 for each pick-up and each put-down;
  • L is the number of lines needed to say every fact after every action;
  • F is the number of those lines that only say “stays the same”.

The changes first, counted from the action lists:

c=6×2+3×3+3×3 =12+9+9=30

Then the lines, our numbers first, each followed by the same step in symbols:

L=12×8=96 L=An F=96−30=66 F=An−c

So 66 of the 96 lines say only that nothing else changes. Written in logic, each of these “stays the same” statements must be spelled out, one for each action and each fact it leaves alone, and their number grows with every new fact and every new action (P&M §6.1.3 calls them frame rules). Having to state everything an action does not change is the frame problem ()Frame problem: The difficulty that a logical description of an action must also state everything the action leaves unchanged, one statement per action and fact (66 of 96 lines in the cup task); STRIPS avoids it with the rule that a fact on neither list keeps its value. Explained in §3.3 Why lists of changes: the frame problem. (FAU AI-1 notes §8.1). An everyday comparison: a recipe says “add the salt”; it never adds “the flour, the oven and the rest of the kitchen stay as they are”.

STRIPS avoids the 66 lines with one rule: a fact that is on neither list keeps its value (P&M §6.1.2). So STRIPS writes the 30 changes and nothing else, which is why a state can be updated by taking out the delete list and putting in the add list, as in Section 3.2.

The price is that every STRIPS action has fixed lists. A move to the table and a move to the door change different facts, so each pair of places needs its own move action (P&M §6.1.2). With 3 places that is 6 moves; Section 4 shows how the count grows, and how a planning language writes all of them at once.

4. PDDL: the task in two files

Key point

To hand the cup task to a planner, we write it in PDDL, the standard language that planners read. STRIPS needs one move action per pair of places, 6 for our 3 places and 90 for 10; PDDL writes one move with the parameters ?from and ?to, and splits the task into a domain file (the predicates and actions, written once) and a problem file (the places, the start state and the goal, one per task).

4.1 One action with parameters

Section 3.3 ended with one STRIPS move action per pair of places. A move leaves one of the places for one of the others:

  • k is the number of places, 3 for the cup task;
  • M is the number of STRIPS move actions.
M=3×2=6 M=k(k−1)

A building with 10 places would need:

M=10×9=90

All 90 say the same thing: be at one place, end at another. So we write the move once, with blanks for the two places, and let the planner fill them in. Such a blank is a parameter ()Parameter (PDDL action): A blank in an action, written with a question mark such as ?from and ?to in move ?from ?to, that the planner fills with objects; one action with parameters replaces many STRIPS actions (6 moves for 3 places, 90 for 10). Explained in §4.1 One action with parameters. of the action, written with a question mark: move ?from ?to (UMBC PDDL notes; LaValle §2.4.1). Facts get blanks too: robot-at ?p stands for the three facts robot-at start, robot-at table and robot-at door. A fact pattern with blanks is a predicate ()Predicate (PDDL): A fact pattern with blanks, such as robot-at ?p, which stands for one fact per object (robot-at start, robot-at table, robot-at door); it lets a domain name a whole family of facts at once. Explained in §4.1 One action with parameters. (LaValle §2.4.1).

The language that writes tasks this way is the Planning Domain Definition Language ()PDDL (Planning Domain Definition Language): The standard language for writing a planning task, defined in 1998 for the International Planning Competition: actions with parameters, preconditions and effects, in a domain file and a problem file; a task written in it can be handed to any planner that reads PDDL. Explained in §4.1 One action with parameters., PDDL, defined in 1998 for the International Planning Competition and read by many planners today (planning.wiki; UMBC PDDL notes). A common language means a robot’s task can be handed to any planner, and a better planner can replace the old one without rewriting the task. PDDL keeps the STRIPS idea: an action’s effect lists the facts it makes true, and the facts it makes false inside (not ...). A PDDL task comes in two files, one for what never changes and one for the task itself, which Sections 4.2 and 4.3 write for the cup task.

4.2 The domain file

The parts of the cup task that never change go in the domain file ()Domain file (PDDL): The PDDL file that holds the parts of a task family that never change: its predicates and its actions; it is written once and reused for every problem in that family. Explained in §4.2 The domain file.: the predicates and the three actions (UMBC PDDL notes). Our domain file, data/cup-domain.pddl:

Reading it line by line:

  • :requirements :strips says that the file uses only the STRIPS features of PDDL: preconditions, add lists and delete lists;
  • :predicates lists the four predicates;
  • each :action has its :parameters, its :precondition, and an :effect that holds the add list (the plain facts) and the delete list (the facts inside not).

The move action with ?from = start and ?to = table is the STRIPS action move start table of Section 3.1, with the same three lists. The many round brackets are the notation of the Lisp programming language, which PDDL keeps (UMBC PDDL notes). The domain file says what the robot can do, but not where it starts or what it must achieve.

4.3 The problem file

What changes from task to task goes in the problem file ()Problem file (PDDL): The PDDL file that holds one task: its objects, its start state and its goal; a new task needs only a new problem file for the same domain file. Explained in §4.3 The problem file.: the objects (here the three places), the start state and the goal (UMBC PDDL notes). Our problem file, data/cup-problem.pddl:

:init is the start state S0 of Section 2.1, and :goal the goal. Figure 5 shows how the files are used: the planner reads both and returns a plan. A new task, such as bringing the cup back from the door to the table, needs only a new problem file with a new :init and :goal (in data/cup-problem-back.pddl); the domain file stays as it is.

Figure 5: The domain file (written once: the predicates robot-at ?p, cup-at ?p, holding-cup, hand-empty and the actions move ?from ?to, pick-up ?p, put-down ?p) and the problem file (one per task: the objects start, table, door, the start state and the goal cup-at door) both go into the planner, which runs forward search and returns the plan: 1 move start table, 2 pick-up table, 3 move table door, 4 put-down door. A note under the problem file: a new task needs only a new problem file

As a check, the notebook reads the two files the way a PDDL planner does: it fills each action’s parameters with the three places and runs breadth-first search (Section 5.1). The search returns the four actions of Section 2.1, and for the cup-back problem file it returns move start door, pick-up door, move door table, put-down table. The files say what the task is; how the planner finds the plan is the subject of Section 5.

5. Forward search: finding the plan

Key point

The last part of the problem is finding the plan without being told it. Forward search starts from the start state, applies every applicable action to make the next states, and searches the resulting graph of states for one that meets the goal; breadth-first search finds the 4-action plan after taking 8 states from the frontier, and A* with a count of the actions still needed takes only 5.

5.1 The state graph, built while searching

The rule of Section 3.2 turns one state into the next. Applied to every applicable action of every state, it links the states into a graph ()Graph: A set of vertices (points) joined by edges (lines), such as the room’s 76 free cells joined by 114 moves; it keeps only which places connect directly, so one search method works for maps, puzzles and any problem of states and moves. Explained in: Graphs and Uninformed Search, §2.1 Cells and moves: vertices and edges, points joined by links: each state is a vertex ()Vertex (graph): One point of a graph, such as one free cell of the room or one waypoint; the places a search moves between. Explained in: Graphs and Uninformed Search, §2.1 Cells and moves: vertices and edges of the graph, and each action is an edge ()Edge (graph): A link between two vertices of a graph, such as one 0.5 m move between two free cells that share a side; it says the search can go directly from one vertex to the other. Explained in: Graphs and Uninformed Search, §2.1 Cells and moves: vertices and edges, a link from one state to the state it leads to (P&M §6.2). The graph is never stored in full; the planner makes a state’s neighbours from the action lists only when it reaches that state, as for the implicit graph ()Implicit graph: A graph never built in full: the search starts from the start vertex and calls a function that returns a vertex’s neighbours when it is expanded, so only the vertices the search reaches are made; this is what makes state spaces of millions of states searchable. Explained in: Graphs and Uninformed Search, §9. Explicit and implicit graphs of route search, a graph whose neighbours are made on demand.

A planner that starts at the start state and moves forward, action by action, until it reaches a state that meets the goal is doing forward search ()Forward search (progression): Planning by starting at the start state, applying every applicable action to make the next states, and searching the resulting graph of states until one meets the goal; any graph search, such as breadth-first search or A*, can run it. Explained in §5.1 The state graph, built while searching., also called progression (P&M §6.2; LaValle §2.4). Any graph search of the earlier Notes can run it. We start with breadth-first search ()Breadth-first search (BFS): A search whose frontier is a queue, so it expands vertices in rings of equal moves from the start; the first route it finds has the fewest moves, which is the shortest only when every move costs the same. Explained in: Graphs and Uninformed Search, §5. Breadth-first search: ring by ring, which keeps a frontier ()Frontier (open list): The vertices a search has reached but not yet expanded, waiting to be taken off one at a time; which one comes off next is what makes one search differ from another. Explained in: Graphs and Uninformed Search, §4. Searching with a frontier and a visited list, the states made but not yet taken, and takes them in the order they were made.

From S0, two actions are applicable: move start table and move start door. pick-up start is not, because the cup is not at the start. So S0 has two neighbours, and the search grows from there. The search took 8 states from the frontier and made 10 of the 12 states the task can reach, the states that some sequence of actions leads to from the start (notebook). The other 244 of the 256 possible sets were never touched. Breadth-first search also returns a plan with the fewest actions, because it looks at all states one action away before any state two actions away. The plan is the one of Section 2.1, now found by the computer.

Eight states is cheap here, but the count grows with the number of facts. With n facts there can be up to 2n states (Section 2.2), so a task with a few more places, cups and doors has far more states for breadth-first search to take, and the search needs a guide.

5.2 A heuristic cuts the search

Section 5.1 took 8 states to find a 4-action plan. A* ()A search:* Dijkstra’s algorithm with the open list sorted by f=g+h, the cost so far plus a heuristic guess of the cost left; with a consistent heuristic it returns the shortest route while expanding far fewer states (9 cells against 54 on the room grid). Explained in: A* and Heuristics, §4.5 The algorithm takes fewer when it has a heuristic ()Heuristic h: A cheap guess of the cost still to go from a state to the goal, such as 3.121 m from the start cell to the door; a search uses it to prefer states that look nearer the goal. Explained in: A* and Heuristics, §2. A guess of the distance left: the heuristic, a guess of the cost still to go, that never overestimates that cost: an admissible heuristic ()Admissible heuristic: A heuristic that is never more than the true cost left from any state, h≤h∗; it makes f a lower bound on every route through a state, so the first route A* takes off the open list is the shortest. Explained in: A* and Heuristics, §5.1 A guess that never overestimates. With every action costing 1, a good guess is the fewest actions still needed, counted like the coffee-delivery example of P&M §6.2:

  • if the cup is at the door: 0;
  • if the robot holds the cup: 1 for the put-down, plus 1 for a move if the robot is not at the door;
  • if the cup lies elsewhere: 3 for pick-up, move and put-down, plus 1 for a move to the cup if the robot is not there.

Each action counted must happen at least once, so the count never overestimates. For the start state S0:

  • g is the cost so far ()Cost so far g (g-value): The length of the best route found so far from the start to a state; A* lowers it whenever a shorter way into the state turns up. Explained in: A* and Heuristics, §4.1 g, h and f on the first step, here the number of actions taken, 0 in S0;
  • h is the heuristic, the fewest actions still needed;
  • f is their sum ()Estimated total cost f (f-value): The cost so far plus the heuristic, f=g+h: the length of the best route through a state if the guess were exact; A* expands the open state with the smallest f. Explained in: A* and Heuristics, §4.1 g, h and f on the first step, the cost A* expects for a plan through the state.
h=1+1+1+1=4 f=g+h=0+4=4

The four 1s are the move to the table, the pick-up, the move to the door and the put-down. Figure 7 runs A* on the same state graph, with the same state names as Figure 6, and writes g + h = f in the corner of each box. A* always takes the frontier state with the smallest f. Watch the frontier list: S2 (f = 5, the robot drove to the door without the cup) and S4 (f = 5, the robot carried the cup back to the start) wait in the frontier, while every state with f = 4 lies on the plan.

Figure 7: A* forward search on the same states as Figure 6, one state taken per frame, with g + h = f in the corner of each box (g: actions so far, h: fewest actions still needed). The first frame shows S0 with 0 + 4 = 4. ‘take S1 (f = 4): makes S3’ (2 + 2 = 4). ‘take S5 (f = 4): makes S7’ (4 + 0 = 4). Last frame: A* takes 5 states, breadth-first search 8; the same 4-action plan in green; S2 (1 + 4 = 5) and S4 (3 + 2 = 5) were made but never taken

A* takes 5 states, S0, S1, S3, S5 and S7, against 8 for breadth-first search, and returns the same 4-action plan (notebook). Our heuristic was written by hand for this one task. Planners built for any task guide forward search with a heuristic too: the default planner of the free planning.domains service is a forward search guided by a heuristic (UMBC PDDL notes). The plan is found; each of its moves still has to be driven.

5.3 From the plan back to routes

The plan of Section 5.2 says “move start table”, not how to drive there. Each move is handed to the route search of the earlier Notes, on the 8-connected grid ()8-connected grid: A grid made into a graph by joining each cell to all 8 cells around it: 4 straight moves of one cell side and 4 diagonal moves of 1.414 cell sides (0.707 m for 0.5 m cells), usually without cutting the corner of a blocked cell; it gives shorter, less jagged routes than a 4-connected grid. Explained in: Dijkstra’s Algorithm and Priority Queues, §2.1 Diagonal moves: the 8-connected grid, the 0.5 m grid with diagonal moves, from the cell of one place to the cell of the next (P&M §6.1 leaves the actions to a lower-level controller in the same way). The last frame of Figure 3 shows the two routes:

  • move start table: one diagonal step, 0.707 m;
  • move table door: 2.707 m.
0.707+2.707=3.414 m

Fetching the cup costs no extra distance, because the table place lies on a shortest route from the start to the door: the plan’s two routes add up to the 3.414 m of the direct route of the Overview (notebook). The task now has its answer: four actions in a fixed order, found by forward search, each move driven by route search.
