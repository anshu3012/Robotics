1. Overview

Key point

A behaviour tree decides what the robot does next by sending a tick from its root every 10 ms; each node answers success, failure or running, and sequences and fallbacks turn those answers into the next step. When the door is blocked, Nav2’s default tree on main checks the path once a second, asks the planner again, and then tries clearing the costmaps, spinning and waiting in turn: the robot reaches the door at 15.60 s instead of 7.37 s, and aborts the goal after six recoveries if no path ever appears.

The robot can already drive round a person the map does not contain. A local planner such as TEBExplained in: TEB: The Timed-Elastic-Band Planner, Start to Finish, §10. The whole drive bends its trajectory round the person every 0.1 s, and Nav2’s DWB controller reaches the door when the plan is remade every secondExplained in: DWA and Nav2’s DWB Controller, Start to Finish, §7.2 The plan remade every second. Both work only while a way to the door exists. When TEB’s trajectory is unsafe it stops and reports a failureExplained in: TEB: The Timed-Elastic-Band Planner, Start to Finish, §9. Step 7: check, command and failure, and the controller server passes the failure on. Neither planner decides what happens next.

The problem of this Note, on numbers. The robot starts at rest at (2.0, 1.0) facing 30° and must stop on the door pose (3.6, 3.5) facing 90°. At 2.4 s a person stops in the gap between the table’s corner and the wall, just left of the door, and a trolley stands in the only other way, between the table and the cabinet. Figure 1 shows the room at 3.01 s. The four gaps left are 0.30 m, 0.47 m, 0.11 m and 0.10 m wide, and the robot is 0.50 m wide, so no path to the door exists. At 8.0 s the person walks away. Between 3.01 s and 8.0 s something must decide:

  • whether the path is still valid, and when to ask for a new one;
  • what to try when the planner finds no path: clear the costmaps, turn, wait or back up, and in which order;
  • when the goal counts as reached, when the robot counts as stuck, and when to abort the goal.

2. Choosing what to do next: the finite state machine

Key point

A finite state machine names each task as a state and draws an arrow for every switch between tasks. Nav2’s recoveries written this way need 12 transitions and a counter, and adding one task, docking when the battery is low, adds 7 more: one from each of the 6 states that can be active, and one back.

The opening’s first need is a rule for what comes after each task: after planning, drive or recover; after a recovery, plan again; after six recoveries, abort.

The idea. The most direct way to write that rule is a flowchart: a box for each task, and an arrow for each way of moving from one box to another, labelled with the event that causes it. A model with a fixed set of states, one of which is active at a time, and transitions between them, each triggered by an event, is a finite state machine (FSM) ()Finite state machine (FSM): A model with a fixed set of states, one of them active at a time, and transitions between them, each triggered by an event, such as Plan, Drive and Spin for a robot; it fixes what comes after each task, but every state must name its own next states, so adding a task means editing many states. Explained in §2. Choosing what to do next: the finite state machine. (Colledanchise and Ögren §2.1). A turnstile is the everyday example: locked, a coin unlocks it; unlocked, a push locks it again.

On the room. Figure 2 writes the blocked-door problem as an FSM with the states Plan, Drive, Clear costmaps, Spin, Wait, Back up, Arrived and Aborted. Look at the arrows into and out of Plan: each recovery state needs an arrow in and an arrow back, and the arrow to take depends on how many plans have already failed, so the machine also needs a counter. Then look at the red dashed arrows: to add docking when the battery is low, every state that can be active needs a new arrow to Dock.

Blue: planning and driving; orange: the four recoveries, each entered when the planner finds no path for the time shown and left back to Plan when it is done; green and grey: the two end states. Grey arrows: its 12 transitions. Red dashed: what docking on a low battery adds, one transition from each of the 6 states that can be active and one back to Plan

The count of transitions, from Figure 2 (notebook):

transitions=6+2+4×1 =12 with docking=12+6+1 =19

The 6 are Plan’s exits (Drive, four recoveries, Aborted), the 2 are Drive’s (back to Plan, Arrived), and each recovery has one exit, back to Plan.

Why it grows. A transition is a one-way jump: the active state must name the state that comes next, for every event. Adding or removing one state therefore means editing every state that can reach it, and the more transitions a machine has to react quickly, the more edits each change needs (Colledanchise and Ögren §1.2). Nav2’s documentation gives the same reason for not using an FSM: navigation as an FSM “may have dozens of states and hundreds of transitions” (Nav2 docs, Behavior Trees). ROS 1’s navigation program, move_base, ran a fixed state machine of this kind (Nav2 start to finishExplained in: Nav2, Start to Finish, §10. ROS 1 move_base compared).

The FSM answers what comes next, but at the price of arrows in every state. Next, a structure in which a task does not need to name the task that comes after it.

3. Behaviour trees: a tick and three answers

Key point

In a behaviour tree, a task never chooses the next task: its parent asks it to run one step, a tick, and it answers success, failure or running. The parents above it decide what comes next, and in Nav2 the root is ticked every 10 ms.

Section 2’s Plan state had to name six next states. The remedy is to let each task report only its outcome, and to place the choice of what comes next in the structure above the tasks.

The idea. A function in a program is called, runs and returns to the caller, which decides what to call next; the function does not jump to another part of the program. A behaviour tree arranges a robot’s tasks in that way (Colledanchise and Ögren §1.2). The tasks are the leaves of a tree. The nodes above them, the control nodes, decide which leaf runs. Each leaf only reports one of three answers.

The standard terms. A behaviour tree (BT) ()Behaviour tree (BT): A tree whose leaves are tasks and checks and whose inner nodes decide, from the leaves’ answers, which leaf runs next, such as Nav2’s tree that plans, follows the path and recovers; no task names another, so tasks can be added or moved without editing the rest. Explained in §3. Behaviour trees: a tick and three answers. is a tree whose leaves are tasks and checks and whose inner nodes decide, from the leaves’ answers, which leaf runs next; it chooses the next task without any task naming another (Colledanchise and Ögren §1.3). A tick ()Tick: The signal a parent node sends to a child to run one step, sent from a behaviour tree’s root at a fixed rate, such as every 10 ms in Nav2; a node runs only while it receives ticks. Explained in §3. Behaviour trees: a tick and three answers. is the signal a parent sends to a child to run one step, starting from the root at a fixed rate; a node runs only while it receives ticks (Colledanchise and Ögren §1.3; BehaviorTree.CPP docs, “Introduction to BT basics”). The return status ()Return status (behaviour tree): A node’s answer to a tick: success when its task is done or its check holds, failure when it cannot be done or the check does not hold, running when it needs more time; the parent decides from it what to tick next. Explained in §3. Behaviour trees: a tick and three answers. is the node’s answer to a tick:

  • success: the task is done, or the check holds;
  • failure: the task cannot be done, or the check does not hold;
  • running: the task needs more time, such as following a path for several seconds.

Two kinds of leaf are used:

  • an action node ()Action node (behaviour tree): A leaf of a behaviour tree that does something, such as asking the planner for a path or turning in place, and answers success, failure or running; it may run for many ticks. Explained in §3. Behaviour trees: a tick and three answers. does something, such as asking the planner for a path or turning in place, and answers success, failure or running;
  • a condition node ()Condition node: A leaf of a behaviour tree that checks something, such as whether the path is still free, and answers success or failure at once, never running; it lets the tree skip or choose tasks. A leaf that takes a long time, such as following a path for 10 s, answers running on every tick until it ends; its parent answers running too, and so on up to the root. In Nav2 most action nodes send a request to a server as a ROS 2 action ()Action (ROS 2): A long job between two nodes, defined in an .action file: the client sends a goal, the server sends feedback while it works and a result when it ends, and the client can cancel, such as driving to a door pose; it is built from three services and two topics. How often. The tick rate sets how fast the tree can detect a change. 4. Sequence and fallback

Key point

A sequence ticks its children in order and stops at the first failure, an “and”; a fallback stops at the first success, an “or”, and a condition placed first in a fallback means “check before you act”. A plain sequence goes on from its running child, while Nav2’s pipeline sequence ticks the children before it again, so its path check runs on every tick.

Section 3’s answers say how each task went. The opening needs them combined: plan, then drive; and plan only when the path is not valid.

The idea. People combine steps in two ways. “Unlock the door, then open it” is an “and”: if unlocking fails, opening is not tried. “Take the lift, or else the stairs” is an “or”: the stairs are tried only if the lift fails.

The standard terms. A sequence node ()Sequence node: A control node that ticks its children from the left and answers failure at the first child that fails, running while a child runs and success when all have succeeded, such as plan and then follow the path; it runs steps that must all happen in order. Explained in §4. Sequence and fallback. ticks its children from the left; it answers failure at the first child that fails, running while a child runs, and success only when every child has succeeded, so it runs steps that must all happen in order. A fallback node ()Fallback node (selector): A control node that ticks its children from the left and answers success at the first child that succeeds, running while a child runs and failure when all have failed, such as keep the path if it is valid, else plan a new one; it tries options in order of preference. Explained in §4. Sequence and fallback., also called a selector, ticks its children from the left; it answers success at the first child that succeeds, running while a child runs, and failure only when every child has failed, so it tries options in order of preference (Colledanchise and Ögren §1.3, Table 1.1). Both are control nodes, written → and ? in Figure 3.

Check before you act. In Figure 3’s tree, the fallback’s first child is the condition “Path valid?“. While the path is valid, the condition succeeds, the fallback succeeds at once, and the planner is not called. Only a failed check leads to ComputePathToPose. A condition placed first in a fallback is how a tree avoids repeating a task whose goal already holds (Colledanchise and Ögren §3.1).

Going on, or checking again. What happens on the next tick decides whether the tree ever detects the person. In BehaviorTree.CPP’s plain Sequence, a child that has succeeded is not ticked again while a later child is running: the next tick goes straight to the running child (BehaviorTree.CPP docs, “Sequences”). Nav2’s PipelineSequence instead ticks every child before the running one again on each tick (Nav2 docs, Nav2-specific nodes).

Watch the left tree from 0.02 s: only FollowPath is ticked. Watch the right tree at 2.40 s: “Path valid?” fails in the tick in which the person appears, and the new path arrives at 2.41 s.

5. Decorators and the blackboard

Key point

A decorator has one child and changes when that child is ticked or what its answer is; Nav2 uses an inverter and a 1 Hz rate controller. The blackboard is the tree’s shared store of named entries, such as the goal, the path and the planner’s error code, through which nodes pass data without knowing one another.

Section 4’s pipeline checks the path 100 times a second. The opening’s robot needs that check only once a second, and needs the planner’s path and error code passed to the nodes that use them.

The idea. A timer on a lamp does not change the lamp; it decides when the lamp may be switched. The word “not” does not change a statement; it turns a true answer into a false one. A decorator node ()Decorator node: A control node with exactly one child that changes when the child is ticked or what its answer becomes, such as an inverter that swaps success and failure or a rate controller that lets a tick through once a second. Explained in §5. Decorators and the blackboard. is a control node with exactly one child that changes when the child is ticked or what its answer becomes, such as flipping success and failure or letting a tick through only once a second (Colledanchise and Ögren §1.3; BehaviorTree.CPP docs, “Introduction to BT basics”). Figure 3 draws it as a rhombus.

On the room. Nav2’s default tree uses two decorators (Nav2 default tree), shown in Figure 5, top:

  • Inverter over the condition GlobalUpdatedGoal?: the condition succeeds only when a new goal has arrived; flipped, its failure becomes success, so the path check can go on when the goal is unchanged;
  • RateController at 1 Hz over the planning part of the tree: it ticks that part at 0.00 s and then 1 s after each success, at 1.01, 2.01, 3.01 and 4.02 s in the run with the person; between those ticks it answers running without ticking it (notebook).

The rate controller’s period is the reason the default tree is slower to detect the person than Figure 4’s pipeline: the person steps in at 2.40 s and the next check is at 3.01 s.

delay=3.01−2.40 =0.61 s

Nav2’s documentation gives the reason for the 1 Hz limit: without it the tree would send the planner a request at the tree’s rate, 100 times a second (Nav2 docs, Detailed behavior tree walkthrough). Between two checks the controller is the part that reacts: in Nav2 it reads the local costmap every 0.05 s (controller_frequency: 20.0, Nav2 nav2_params.yaml) and steers round the person, as TEB and DWB do. Our stand-in follower does not, and at 3.01 s it is still 0.31 m from the person (notebook).

6. Nav2’s default tree, tick by tick

Key point

Nav2’s default tree on main keeps a path while the goal is unchanged, less than 4 m of path is left and the path is free, checks this once a second, and asks for a new path only when one of the three fails; the trees of the released versions (Humble, Jazzy, Kilted) remake the path at every check. With the person stepping in at 2.4 s, the tree on main asks for two paths, at 0.01 s and 3.02 s, and the goal is accepted at 9.77 s.

The opening’s first question, whether the path is still valid and when to ask for a new one, is settled by the whole of Nav2’s default tree, navigate_to_pose_w_replanning_and_recovery.xml (Nav2 default tree), built from the parts of Sections 3 to 5.

The two halves. The root is a RecoveryNode with two children (Nav2 docs, Detailed behavior tree walkthrough):

  1. navigation, a PipelineSequence: five selector nodes that pick the planner, controller, goal checker, progress checker and path handler by name; then, under the 1 Hz RateController, the planning part; then FollowPath;
  2. recovery, ticked only when navigation fails: Section 7.

A RecoveryNode ticks its first child; if that child fails, it ticks the second child, and if the second succeeds it ticks the first again, up to a set number of retries (Nav2 docs, Nav2-specific nodes). The root allows 6 retries; the planning part and FollowPath each sit in a RecoveryNode with 1 retry, whose second child clears the matching costmap (Section 7).

When to plan again. The planning part is a fallback whose first child is a check, CheckIfNewPathNeeded, a ReactiveSequence of four nodes that must all succeed for the old path to be kept:

  • Inverter over GlobalUpdatedGoal?: the goal has not changed;
  • IsGoalNearby?: less than 4.0 m of path is left from the robot (proximity_threshold="4.0");
  • TruncatePathLocal: writes the part of the path from the robot on to the entry remaining_path;
  • ValidatePath?: for a round robot, no pose of remaining_path is inside an obstacle or closer to one than the robot’s radius (nav2_planner, is_path_valid_service.hpp).

If any of the four fails, the fallback ticks ComputePathToPose. The documentation gives the reason for keeping the path near the goal: planning again close to the goal can make the robot loop, because of drift in its position estimate and errors in following the path (Nav2 docs, Detailed behavior tree walkthrough). The path in the room is short enough for that rule to apply from the start (notebook):

path length=3.38 m<4.0 m

So in the room the tree plans again only when the path is blocked. On a longer path, such as Section 9’s 5.27 m path to waypoint 1, IsGoalNearby? fails and the tree plans again at every 1 Hz check until less than 4 m is left.

Released versions. CheckIfNewPathNeeded exists only in the tree on main. In the default trees of Nav2’s released versions (Humble, Jazzy, Kilted), the RateController ticks ComputePathToPose directly, so the path is remade once a second whether or not the old one is still valid, as in the blue run of DWA and DWBExplained in: DWA and Nav2’s DWB Controller, Start to Finish, §7.2 The plan remade every second (Nav2 default tree, branches humble, jazzy, kilted). This Note follows main.

7. Recovery behaviours: when no path exists

Key point

When the planner finds no path, the default tree first clears the global costmap and asks again; if that fails, it runs one recovery behaviour from a fixed round: clear both costmaps, spin 1.57 rad, wait 5 s, back up 0.30 m, and plans again after each. On the blocked door, the third recovery, the wait, lasts until the person has left, and the goal is accepted at 15.60 s; if the person stays, the tree fails after six recoveries at 13.58 s.

The opening’s second question is what to try between 3.01 s and 8.0 s, when the gaps of Figure 1 leave no path.

The idea. A person whose way is blocked has a few standard responses: look again in case the obstacle was misjudged, turn to look round, wait for the way to clear, or step back. Nav2 gives the robot the same set of actions. An action that changes the robot’s state or its map so that a failed step may succeed when tried again is a recovery behaviour ()Recovery behaviour: An action that changes the robot’s pose or its map so that a failed step, such as planning a path, may succeed when tried again; Nav2’s are clearing the costmaps, spinning, waiting and backing up, taken in turn. Explained in §7. Recovery behaviours: when no path exists. (Nav2 docs, Navigation Servers; Zheng §6). Each of Nav2’s four has its own purpose:

  • clear the costmaps: erase the obstacle marks, for marks that come from sensor faults and no longer exist (Nav2 docs, Navigation Servers);
  • spin: turn in place by 1.57 rad, which can bring a robot stuck in a poor heading into free space it can drive through (Nav2 docs, Navigation Servers; Zheng §6);
  • wait: stand still for 5 s, which gives a passing problem, such as a crowd of people, time to clear (Nav2 docs, Navigate Through Poses);
  • back up: drive 0.30 m backwards at 0.15 m/s, out of a tight spot (Nav2 docs, Navigation Servers; Zheng §6).

The spin, wait and back-up actions run in Nav2’s behaviour server, behavior_server, the program that holds such actions and shares the local costmap between them (Nav2 docs, Navigation Servers).

First, a recovery for the failed step. When ComputePathToPose fails, its RecoveryNode (1 retry) ticks a sequence: WouldAPlannerRecoveryHelp?, then clear the global costmap. The condition reads compute_path_error_code from the blackboard and succeeds only for NO_VALID_PATH, TIMEOUT or UNKNOWN; a goal outside the map, for example, is not worth a recovery (nav2_behavior_tree, would_a_planner_recovery_help_condition.cpp). The same holds for FollowPath: its retry clears the local costmap, for the controller’s errors UNKNOWN, PATIENCE_EXCEEDED, FAILED_TO_MAKE_PROGRESS and NO_VALID_CONTROL.

Then the round of four. If the step still fails, the whole navigation half fails and the root ticks the recovery half (Nav2 default tree):

  1. a fallback asks whether a recovery can help, with the same two error checks;
  2. a ReactiveFallback ticks GoalUpdated? first, so a new goal stops any recovery at once;
  3. otherwise a RoundRobin ticks one of its four children: clear both costmaps, Spin, Wait, BackUp.

A RoundRobin remembers its place: after one child succeeds, the next time it is ticked it starts from the following child, and after the last it wraps round to the first (Nav2 docs, Nav2-specific nodes). Each successful recovery uses one of the root’s 6 retries, and the navigation half runs again.

8. The goal checker and the progress checker

Key point

The goal checker accepts the goal once the robot is within 0.25 m of the goal position and then within 0.25 rad of its heading, and does not check the position again while the robot turns. The progress checker fails FollowPath when the robot has not moved 0.5 m from its last checkpoint in 10 s.

The opening’s third question: when does the goal count as reached, and when does the robot count as stuck?

The idea. A robot never stops exactly on a pose: localisation and control leave errors of centimetres. A rule must say how close is close enough. And a robot whose wheels turn while it stands still, held by a cable or a doorstep, looks to the planner like a robot on its way; another rule must notice that nothing is changing.

The standard terms. Both checks run inside Nav2’s controller server, on every control cycle (nav2_controller, simple_goal_checker.cpp and simple_progress_checker.cpp; Nav2 nav2_params.yaml):

  • a goal checker ()Goal checker: The test a controller runs to decide that the robot has reached its goal, such as Nav2’s default: the position within 0.25 m, then the heading within 0.25 rad, with the position kept as reached while the robot turns; it ends the path-following action with success. Explained in §8. The goal checker and the progress checker. is the test the controller runs to decide that the robot has reached its goal; Nav2’s default requires less than path_length_tolerance, 1.0 m, of path left, the position within xy_goal_tolerance, 0.25 m, and then the heading within yaw_goal_tolerance, 0.25 rad, and with stateful: true it keeps the position as reached while the robot turns on the spot;
  • a progress checker ()Progress checker: The test a controller runs to decide that the robot is stuck, such as Nav2’s default: a failure when the robot has not moved 0.5 m from its last checkpoint in 10 s; it turns a robot that does not move into an error the recovery behaviours can act on. Explained in §8. The goal checker and the progress checker. is the test that decides the robot is stuck; Nav2’s default stores a checkpoint, moves it to the robot whenever the robot is more than required_movement_radius, 0.5 m, from it, and fails when movement_time_allowance, 10 s, passes without that.

9. Waypoint following

Key point

Nav2’s waypoint follower sends a list of poses one at a time, each as its own navigation goal; after each pose reached it runs a task, by default a 200 ms pause, and with stop_on_failure: false it records a failed pose as missed and goes on to the next. In the room, waypoint 2, which the person and the trolley shut off, is missed after six recoveries and waypoint 3 is reached at 34.41 s.

The opening’s robot had one goal. A patrol, a delivery round or an inspection has a list, and the person at the door may block one pose of the list while the others stay reachable.

The idea. A delivery driver with a list of addresses drives to each in turn, leaves the parcel, and drives on; if one street is closed, the driver notes the address as missed and goes on to the next one instead of ending the round.

The standard term. Waypoint following ()Waypoint following: Driving a robot through a list of poses in order, sending each as a separate navigation goal and running a task, such as a pause, at each one reached; a failed pose can be recorded as missed so the rest of the list still runs. Explained in §9. Waypoint following. is driving a robot through a list of poses in order, sending each as a separate navigation goal and, at each pose reached, running a task such as a pause or a photograph; the program that does it in Nav2 is waypoint_follower (Nav2 docs, Navigation Servers). Its rules, from its code and Nav2’s bring-up file (nav2_waypoint_follower, waypoint_follower.cpp and wait_at_waypoint.cpp; Nav2 nav2_params.yaml):

  1. send waypoint i as a NavigateToPose goal and wait for its result, checking 20 times a second (loop_rate: 20);
  2. if it succeeds, run the task executor at the waypoint: WaitAtWaypoint, a pause of 200 ms (waypoint_pause_duration: 200);
  3. if it fails, add it to the list of missed waypoints; with stop_on_failure: false go on, otherwise stop the whole list;
  4. go on to waypoint i + 1; at the end, report the missed waypoints.

Nav2 also offers NavigateThroughPoses, a single navigation goal that plans one path from the robot through all the poses to the last (Nav2 docs, Navigate Through Poses); the robot then does not stop at each pose, and no task runs there.

10. How cars switch behaviours: Apollo and Autoware

Key point

Apollo’s planner chooses one scenario at a time from a list in priority order and runs it as a fixed chain of stages, each naming the next, a state machine; Autoware’s behaviour path planner runs scene modules in slots, and a module that asks to run joins a candidate list and, once approved, an approved list run in series.

The opening’s robot needed to decide when to replan, recover and stop. A car must decide when to follow its lane, stop at a sign, give way, change lanes or pull over, every 0.1 s, and two open-source driving stacks make that choice in two different ways.

10.1 Apollo: scenarios and stages

The idea. A driver approaching a stop sign runs through fixed steps: slow to stop at the line, wait until the cars that arrived first have gone, edge forward to see, then cross. Apollo writes each such situation as a fixed list of steps.

The standard terms. A scenario ()Scenario (Apollo planning): One driving situation in Apollo’s planning module with its own planning steps, such as following the lane, a stop sign or pulling over; a scenario manager picks one per 0.1 s cycle, the first in a fixed order that applies. Explained in §10.1 Apollo: scenarios and stages. in Apollo’s planning module is one driving situation with its own planning steps, such as following the lane, a stop sign or pulling over; a scenario manager picks one per planning cycle. A stage ()Stage (Apollo planning): One step of an Apollo scenario, such as stopping at the line or creeping forward at a stop sign, with its own rule for when it ends and which stage comes next; the stages of a scenario form a state machine. Explained in §10.1 Apollo: scenarios and stages. is one step of a scenario, with its own rule for when it ends and which stage comes next. Their rules, read from Apollo’s code (Apollo, modules/planning):

  • planning runs every 0.1 s (planning_loop_rate, 10);
  • the scenario manager checks the scenarios in the configured order, from EMERGENCY_PULL_OVER to LANE_FOLLOW, 12 in all (planner_config.pb.txt); it switches to the first one that applies, but keeps the current one while it is running unless one earlier in the list applies (scenario_manager.cc);
  • when a stage ends it names the next stage; when the last ends, the scenario is done and the manager chooses again (scenario.cc).

The stages of the stop-sign scenario, STOP_SIGN_UNPROTECTED, and the rules that end them (Apollo, folder stop_sign_unprotected, scenario_conf.pb.txt):

  1. PRE_STOP, entered when the car’s front is 4.0 m or less before the stop line: ends when the car has stopped, at 0.2 m/s or less, at most 2.0 m before the line; meanwhile it puts every vehicle within 5.0 m of its own stop line on a crossing lane on a watch list;
  2. STOP: ends after at least 1.0 s, once every watched vehicle is more than 10.0 m from its stop line, or after 8.0 s with at most one left;
  3. CREEP: edges forward; ends when the front is 2.0 m past the line, or after 10.0 s, and no moving obstacle can reach the car’s path within 6.0 s, for 5 cycles in a row;
  4. INTERSECTION_CRUISE: ends when the car’s rear is 20.0 m past the line, when the map has no junction outline; the scenario is then done.

10.2 Autoware: scene modules in slots

The idea. Some driving tasks must run together: a car changing lanes may meet a parked car in the new lane and must steer round it while the lane change goes on. A single active state cannot express that.

The standard term. A scene module ()Scene module (Autoware): A plug-in of Autoware’s behaviour path planner for one driving task, such as a lane change or avoiding a parked car, that asks to run when its situation arises and changes the path it is given; several approved modules can run at once, in series. Explained in §10.2 Autoware: scene modules in slots. in Autoware’s behaviour path planner is a plug-in for one driving task, such as a lane change, avoiding a parked car or pulling into a goal, that asks to run when its situation arises and changes the path it is given (Autoware, manager design document). Its rules, from that design document and the code on main (Autoware, scene_module_manager.param.yaml, planner_manager.cpp, scene_module_interface.hpp):

  • the planner runs 10 times a second (planning_hz: 10.0, behavior_path_planner.param.yaml) and passes the lane’s centre line through four slots in turn, each slot taking the path from the one before;
  • within a slot, a module listed earlier has priority;
  • a module that asks to run becomes a candidate if the approved modules allow it; candidates run side by side on the approved path, waiting for approval;
  • an approved module moves to the approved stack, where modules run in series, each taking the path of the one before;
  • each module is in one of five states, IDLE, RUNNING, WAITING_APPROVAL, SUCCESS and FAILURE; a module that fails is removed together with every module approved after it.
