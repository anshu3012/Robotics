1. Overview

Key point

Every cycle, teb_local_planner cuts the global plan at the edge of its costmap, turns every occupied cell into an obstacle point, keeps up to 5 timed elastic bands that pass obstacles on different sides, optimises each with 4 passes of 5 Levenberg–Marquardt steps, picks the cheapest, checks its first poses and sends the speed of its first piece. On the room, our Python version of that algorithm passes the person 0.137 m clear and stops on the door pose at 9.8 s.

The robot can already avoid a person the map does not contain. Explained in: Trajectory Optimisation: The Local Planner, §2.1 Levels of planning, a timed elastic band ()Timed elastic band (TEB): A trajectory written as a list of poses with the time between neighbours, optimised for the least total time while penalties keep the motion rule, the speed and acceleration limits and the clearance from obstacles; a ROS and Nav2 local planner that solves it again every cycle from its last answer. Explained in: Trajectory Optimisation: The Local Planner, §5.1 Poses with time steps, solves an optimisation problem every 0.1 s and stops on the door pose at 8.0 s, against 6.7 s in a clear room. Nav2’s DWB controller, in DWA and DWBExplained in: DWA and Nav2’s DWB Controller, Start to Finish, §7. The whole drive: DWB against TEB, stops in front of the person when the plan is made once, and is accepted at the door at 13.3 s when the plan is remade every second.

RO-058’s band, however, was a teaching version of TEB, not the package a robot runs:

  • it measured distances to the exact shapes of the table and the person, while the package receives only the cells of a costmap;
  • it limited each wheel to 0.6 m/s, while the package has one limit for speed and one for turn rate;
  • it kept one band, so with the person 0.25 m further left its warm start entered the gap between person and table and overlapped the person by 0.02 m (local minimaExplained in: Trajectory Optimisation: The Local Planner, §7. Local minima and warm starts);
  • it never said which pose the package aims at, which of several bands it sends, or what it does when a band is unsafe.

This Note takes the real package, teb_local_planner, start to finish: what goes in, every step in the order its code runs them, and what comes out. The problem of one cycle, on numbers: at 2.4 s the robot drives at 0.5 m/s, a person it has never seen stands on its plan, and within the next 0.1 s TEB must turn a 3.698 m plan and 590 occupied costmap cells into one forward speed and one turn rate.

What we ran. The runs in this Note are our own Python version of teb_local_planner’s algorithm (images/tebkit.py), written from its code on the branch ros2-master, the one Nav2 uses, with its parameter values. Our version is not the package running: it follows the same steps in the same order, and we simplified four things:

  • the solver: g2o’s sparse Levenberg–Marquardt is replaced by our own, with the same cost terms, the same 4 passes of 5 steps and g2o’s rule for the step size, but with derivatives by finite differences and no sparse linear algebra;
  • the costmap: a cell is occupied when a shape of the room covers it, with no sensor; the safety check tests every occupied cell inside the robot’s disk, while Nav2’s tests the cells under the disk’s outline;
  • the roadmap’s random points come from a generator with a fixed seed, so every run repeats;
  • planning takes no time: each command is applied at once for the next 0.1 s.

2. Where TEB sits: inputs, outputs, parameters

Key point

In Nav2, TEB is a controller plugin from its own repository. Each cycle the controller server passes it the robot’s pose and speed; it reads the global plan it was given and the local costmap, and returns one forward speed and one turn rate, or an error. Its parameters default to the values in teb_config.h; we change six for our robot and room.

The opening’s problem starts with the inputs: before TEB can turn a plan and some cells into a command, the controller server must give it the plan, the cells and the robot’s state, every 0.1 s.

2.1 A controller plugin

The idea. Nav2 runs one program, the controller server, that calls a controller every cycle; which controller is a setting. A piece of code that a program loads by name from a setting, instead of having it built in, is a plugin. TEB is such a plugin: the package’s example file for Nav2 loads teb_local_planner::TebLocalPlannerROS under the name FollowPath (teb_local_planner, params/teb_params.yaml). TEB is not part of Nav2’s own repository: Nav2’s list of plugins names it as a third-party controller and links to rst-tu-dortmund/teb_local_planner (Nav2 docs, navigation plugins). In ROS 1 the same planner is a plugin of move_base (teb_local_planner, noetic-devel). Nav2 start to finishExplained in: Nav2, Start to Finish, §3. One goal, message by message follows one goal through every Nav2 server.

The controller server calls TEB three ways (teb_local_planner, src/teb_local_planner_ros.cpp):

  1. configure(), once: read the parameters and build the planner, with several bands if enable_homotopy_class_planning is true (the default), or one;
  2. setPlan(), whenever the global planner sends a new plan: TEB stores it and does not start again;
  3. computeVelocityCommands(), every cycle: the robot’s pose and speed go in; a speed and a turn rate come out, or an error.

2.3 The parameters, and the six we change

In ROS 2 every parameter the file does not set keeps the value written in the constructor of TebConfig in include/teb_local_planner/teb_config.h (ros2-master); ROS 1 took its defaults from cfg/TebLocalPlannerReconfigure.cfg, and several differ, such as max_global_plan_lookahead_dist, 1.0 m in the C++ file and 3.0 m in the ROS 1 file. We use the C++ defaults and change six:

  • max_global_plan_lookahead_dist 3.0 m (C++ default 1.0 m), as in the ROS 1 file and the package’s Nav2 example file;
  • max_vel_x 0.5 m/s and max_vel_theta 1.0 rad/s (defaults 0.4 m/s and 0.3 rad/s), our robot’s limits, explained below;
  • acc_lim_x 0.5 m/s², our robot’s, the same as the default;
  • acc_lim_theta 10 rad/s² (default 0.5): our robot’s model changes its turn rate at once, so we set this limit high enough never to bind;
  • min_obstacle_dist 0.1 m (default 0.5 m), RO-058’s clearance for the small room;
  • xy_goal_tolerance 0.02 m (default 0.2 m): in Nav2 the goal checker passes its tolerance in, and we use RO-058’s arrival test, within 0.02 m and 0.05 rad, stopped.

Two limits for a robot with one. TEB limits the speed and the turn rate separately, while our robot’s limit is on each wheel. 3. Step 1: the plan ahead and the local goal

Key point

TEB drops the plan behind the robot, keeps it from the pose nearest the robot to the first pose more than 85 percent of half the costmap’s width away, 1.275 m in a 3 m costmap, and makes that pose the local goal, facing the average direction of the plan’s next three pieces. At 2.4 s that is 32 poses and a local goal 1.29 m ahead, facing 90°.

The opening’s plan is 3.698 m long, but the band can only avoid what the costmap shows, at most 1.5 m to each side of the robot. TEB needs a goal inside that window.

The idea. A driver who follows a long route on a navigation display aims at the farthest point the display shows. TEB does the same, with the local costmap as the display. RO-058 called the pose it aims at the local goal ()Local goal (virtual goal): The pose on the global plan at the end of the local planner’s window, facing along the plan, which the local planner plans to reach; it moves along the plan with the robot, and becomes the real goal when that comes within reach. Explained in: Trajectory Optimisation: The Local Planner, §2.2 The global plan and the local planner in numbers and took it 1.5 m along the route; the code takes it differently (teb_local_planner, pruneGlobalPlan(), transformGlobalPlan(), estimateLocalGoalOrientation()):

  1. prune: drop the plan’s poses before the first one within global_plan_prune_distance, 1 m, of the robot; at 2.4 s the robot is still within 1 m of the plan’s start, so nothing is dropped;
  2. cut: from the plan’s pose nearest the robot, keep poses until one lies further from the robot than 85 percent of half the costmap’s width, or until the kept plan is longer than max_global_plan_lookahead_dist, 3 m; that pose is kept and is the local goal;
  3. turn: face the local goal along the average direction of the plan’s next three pieces after it; near the plan’s end, use the end pose’s own heading.

A pitfall. In a 3 m costmap the local goal is never more than about 1.3 m ahead, whatever max_global_plan_lookahead_dist says above that; and the C++ default of 1.0 m would cut the plan sooner than the costmap does. To plan further ahead, the costmap must grow, which costs time (Section 4). The local goal is set; next, the obstacles the band must keep away from.

4. Step 2: obstacles from the costmap

Key point

TEB does not get the room’s shapes: every lethal cell of the local costmap becomes a point obstacle, 534 of them at 2.4 s. Each pose of a band then reads only a few of them, the nearest on its left and on its right and any very close, through the robot’s footprint model, here a circle of radius 0.25 m.

The opening’s 590 cells are the only information TEB has about the person, the table and the walls. This step turns them into obstacles the optimiser can measure distances to.

4.1 Cells become point obstacles

The idea. Consider the costmap as squared paper with the blocked squares shaded. TEB marks the centre of every shaded square and treats each mark as an obstacle of zero size.

The standard terms. A costmap cell that holds an obstacle, with the highest cost, 254 in Nav2, so that a robot centred on it would certainly collide, is a lethal cell ()Lethal cell: A costmap cell that holds an obstacle, with the highest cost (254 in Nav2), so that a robot centred on it would certainly collide; local planners such as TEB turn these cells into the obstacles they avoid. Explained in §4.1 Cells become point obstacles. (navigation2, cost_values.hpp). An obstacle given as one point, the centre of a lethal cell, which the optimiser keeps the robot’s footprint away from, is a point obstacle ()Point obstacle: An obstacle given as a single point, such as the centre of one lethal cell; TEB by default makes one per lethal cell of its local costmap and keeps the robot’s footprint a set distance from each, so its computing time grows with the number of cells. Explained in §4.1 Cells become point obstacles. (teb_local_planner). TEB’s default has no other step: updateObstacleContainerWithCostmap() adds one point obstacle per lethal cell, except cells behind the robot and further than costmap_obstacles_behind_robot_dist, 1.5 m (teb_local_planner).

At 2.4 s (Figure 6):

4.2 The footprint model and which obstacles each pose reads

The idea. To keep the robot off a point, TEB needs the distance from the robot’s body to the point. The body can be described coarsely or exactly; coarser is faster.

The standard term. The shape TEB uses for the robot when it measures the distance to an obstacle, one of a point, a circle, two circles, a line or a polygon, is the footprint model ()Footprint model: The shape a local planner uses for the robot when it measures the distance to an obstacle: in TEB a point, a circle, two circles, a line or a polygon; a coarser shape is faster to compute, a closer one wastes less room, such as two circles or a polygon for a car. Explained in §4.2 The footprint model and which obstacles each pose reads. (teb_local_planner, robot_footprint_model.h). Figure 7 draws all five round RO-055’s car. Our robot is a disk, so we use the circle of radius 0.25 m: the distance to an obstacle point is the distance from the robot’s centre minus 0.25 m.

Figure 7: TEB’s five footprint models (parameter footprint_model.type), drawn round RO-055’s car, 4.0 m by 1.8 m (dashed), whose pose is the middle of its rear axle (grey dot). Blue: the model; red: the distance to an obstacle point that the obstacle terms use. point: to the pose; circular: to the pose minus a radius, 3.37 m to cover the car; two_circles: the nearer of two circles along the car; line: to a segment, with no width, so min_obstacle_dist must cover the half width; polygon: to the outline. A band of 24 poses and 534 points would make over 12 000 pairs. TEB keeps few: for each pose except the first and the last it takes (teb_local_planner, AddEdgesObstacles()):

  • every point closer than 1.5 times min_obstacle_dist, 0.15 m from the footprint;
  • of the rest within 5 times min_obstacle_dist, 0.5 m, the nearest one on the pose’s left and the nearest on its right.

The band picked at 2.4 s keeps 28 pairs (Figure 6). Each pair adds two penalties, with:

  • d, the distance from the robot’s disk to the obstacle point, in m, 0.1473 for the closest pair;
  • dmin​, min_obstacle_dist, 0.1 m;
  • ϵ, penalty_epsilon, the margin added to every limit, 0.05 m;
  • dinf​, inflation_dist, 0.6 m;
  • eobs​, how far the disk comes within the clearance plus the margin, in m;
  • einf​, how far it comes within the inflation distance, in m.
eobs​=0.1+0.05−0.1473 =0.0027 m einf​=0.6−0.1473 =0.4527 m eobs​=max(0, dmin​+ϵ−d) einf​=max(0, dinf​−d)

Each is squared and weighted: the first by weight_obstacle, 50, giving 0.0004; the second by weight_inflation, 0.1, giving 0.0205 (notebook). The second term is small but reaches out to 0.6 m, so it moves the band slightly away from obstacles even when the clearance holds (teb_local_planner, EdgeInflatedObstacle). The obstacles are ready; next, the bands that will be pushed away from them.

5. Step 3: warm start, or start again

Key point

Each band from the last cycle is moved to the robot and the new local goal and kept as the first guess, unless the local goal has jumped 1 m or turned 90° or more, in which case every band is dropped. A band is also built from the plan, a pose at every plan point, timed at full speed. At 2.4 s both first guesses run through the person.

The opening’s band must be found in one cycle; an optimiser needs a first guess, and TEB has two kinds.

The warm start. The first kind is the band of the last cycle, a warm start ()Warm start: Starting a solver from an earlier answer, such as the last cycle’s trajectory or a planner’s path, instead of from scratch; each solve then only corrects a nearby answer, and the starting point also decides which local minimum it reaches. Explained in: Trajectory Optimisation: The Local Planner, §2.3 One optimisation, two loops: RO-058’s loop drops the poses the robot has passed, moves the first pose to the robot and the last to the new local goal (teb_local_planner, updateAndPruneTEB()). The package adds a rule RO-058 did not need (updateAllTEBs()): if the new local goal lies 1.0 m or more from the old one (force_reinit_new_goal_dist), or faces 90° or more away from it (force_reinit_new_goal_angular, π/2 on ros2-master, 0.78 rad in ROS 1), every band is dropped, because a band shaped for one goal is a poor first guess for a very different one.

In our drive the rule fires once (Figure 8, bottom). Until 4.6 s the local goal faces along the plan’s last piece, which heads down to the door pose at −35.54°; at 4.7 s the local goal, now 0.143 m from the plan’s end, takes the door pose’s own heading, 90° (Section 3, step 3) (notebook):

90−(−35.54)=125.54∘

which is more than 90°, so the bands are dropped and a new one is built from the plan. In the clear room the same happens at 4.1 s.

The band from the plan. The second kind is built each cycle from the kept plan (initTrajectoryToGoal()): a pose at every plan point, facing the next point, and between neighbours the time to drive there at max_vel_x or to turn there at max_vel_theta, whichever is longer.   • Δθ, its turn, in rad;

Key point

The standard term. 6.2 Finding new classes: a random roadmap

The idea. To find routes past obstacles that no band covers yet, TEB places a few random points between the robot and the local goal, connects those that lie ahead of one another without crossing an obstacle, and lists every path through them.

The mechanism. The steps, in the order the code runs them (renewAndAnalyzeOldTebs(), exploreEquivalenceClassesAndInitTebs(), ProbRoadmapGraph::createGraph(), DepthFirst()):

  1. compute the class of every band kept from the last cycle, last cycle’s best first, and drop a band whose class is already taken;
  2. drop a band that sets off more than 90° away from the best band’s direction, or takes more than 3 times as long;
  3. add the band from the plan if its class is new;
  4. scatter roadmap_graph_no_samples, 15, random points in a rectangle from the robot to the local goal, roadmap_graph_area_width, 6 m, wide;
  5. join two points by an edge when it heads forward, its direction within about 63° of the robot-to-goal direction (a cosine above obstacle_heading_threshold, 0.45), and passes no point obstacle closer than min_obstacle_dist, 0.1 m (the robot’s radius is not added here);
  6. list every path from the robot to the local goal with depth-first search ()Depth-first search (DFS): A search whose frontier is a stack, so it always extends the newest path and dives deep before backing up; it backs up to its last untried choice at dead ends and finds a route, but which one, and how long, depends on the order the moves are tried (22 moves where breadth-first search found 8). Explained in: Graphs and Uninformed Search, §6. Depth-first search: dive, then back up; build a band on each path and keep it if its class is new, until there are max_number_classes, 5, bands.

The random points and edges form a small probabilistic roadmap ()Probabilistic roadmap (PRM): A graph of random free configurations (milestones) joined by straight edges that pass a collision check, built once and then searched with A*; it describes the free space without building the obstacle region, so it scales to robots with many joints. 7. Step 5: optimise every band: the g2o graph

Key point

Each candidate becomes a graph whose vertices are its poses and time steps and whose edges are its cost terms, each joining the few vertices it reads. TEB optimises every band separately, in parallel, with 4 passes of 5 Levenberg–Marquardt steps, and plans each band to stop at its local goal.

The opening’s one speed and turn rate will come from a band, but the candidates of Section 6 are unrefined first guesses that still run through or close past the person. This step makes each one fast, smooth and clear.

The cost is RO-058’s: the sum of the squared time steps plus squared penalties for every broken limit, time plus penaltiesExplained in: Trajectory Optimisation: The Local Planner, §5.2 The cost: time plus penalties, solved by sparse least squaresExplained in: Trajectory Optimisation: The Local Planner, §5.3 Solving it: sparse least squares with the Levenberg–Marquardt method ()Levenberg–Marquardt method: A solver for sums of squares that takes Gauss–Newton steps, jumping to the lowest point of a bowl built from straight-line guesses of each term, blended with a small step downhill that grows when a step fails and shrinks when it succeeds; it converges fast near the answer and safely far from it. Explained in: Trajectory Optimisation: The Local Planner, §5.3 Solving it: sparse least squares in g2o ()g2o: A library that solves sparse least-squares problems written as a graph, each term joining a few variables, with Gauss–Newton or Levenberg–Marquardt steps; TEB solves its band with it. Explained in: Trajectory Optimisation: The Local Planner, §10.1 Solvers, and path then speed. What is new here is how the code builds it.

The idea. The problem resembles beads joined by elastic cords: each pose and each time step is a bead, and each cost term is a cord attached to the beads it depends on. The speed term is attached to two poses and the time between them, the acceleration term to three poses and two time steps. g2o stores the problem in this form.

The standard term. In g2o’s graph, one cost term, joined to the vertices it reads, the poses and time steps whose values change its error, is an edge ()Edge (g2o graph): One cost term of a graph optimisation, joined to the vertices whose values it reads, such as TEB’s acceleration term joined to three poses and two time steps; because each edge touches only a few vertices, the problem is sparse and fast to solve. 8. Step 6: pick the cheapest band

Key point

TEB scores each optimised band by the sum of all its edges’ weighted squared errors, with the obstacle edges multiplied by 100, and multiplies the score of the band in the global plan’s class by 0.95. The band with the lowest score is chosen: with the person 0.25 m further left, the band on the left, 59.023 against 314.226 and 348.884.

The opening’s question of which side ends here: the cycle must send the speed of one band.

The idea. Every band receives one score: time adds a small amount, every exceeded limit more, and proximity to an obstacle the most. The band in the global plan’s class receives a 5 percent reduction, so that between bands of nearly equal score TEB keeps to the global plan’s side (the code’s comment calls it a small hysteresis), and the band with the lowest score is chosen.

The mechanism. After the last pass, computeCurrentCost() adds up the weighted squared errors of every edge of the band, with the obstacle weight of that pass, 50 doubled three times, 400, and with every obstacle edge multiplied by selection_obst_cost_scale, 100. selectBestTeb() then multiplies (teb_local_planner, src/homotopy_class_planner.cpp):

  • the cost of last cycle’s best band by selection_cost_hysteresis, 1.0, so no hysteresis by default;
  • the cost of the band in the global plan’s class by selection_prefer_initial_plan, 0.95;

and picks the lowest. At 2.5 s with the person 0.25 m further left (notebook):

Key point

TEB checks the robot’s footprint at the band’s first 6 poses against the costmap’s lethal cells; if any touches, it drops all bands and sends nothing. When there is no command. In five cases TEB drops all its bands, so the next cycle starts again, and throws an error to the controller server instead of a command (computeVelocityCommands()):

  • the planner fails;
  • the solution diverged, a test that is off by default (divergence_detection_enable);
  • the feasibility check fails;
  • the first piece gives no valid command, such as a time step of 0;
  • for a car, the steering angle is not finite.

The controller server stops the robot; if the failures last longer than its failure_tolerance, 0.3 s in Nav2’s bring-up file, it aborts the path-following action, and Nav2’s behaviour tree decides what to do, such as clear the costmap or back up (Nav2 nav2_params.yaml; behaviour trees and recoveryExplained in: Behaviour Trees and Recovery: Deciding What the Robot Does Next, §7.   • oscillation recovery: it keeps the last 10 s of commands, each divided by its limit; if their mean speed and mean turn rate are both below 0.1 and the turn rate has changed sign more than once, it adds an edge of weight 50 that favours the current turning direction for the first 3 turns, for 10 s (recovery_behaviors.cpp).

Key point

12. DWA, TEB and MPC compared

Key point

In the authors’ benchmark, TEB needs the least computing per step, 5.9 ms against 19.1 ms for the dynamic window’s rollout and 12.5 to 15.8 ms for full model predictive control, and drives about as fast; the authors conclude that for a differential drive TEB need not be replaced.

The opening’s cycle must fit in 0.1 s on a real computer, and the room is one test; a benchmark answers both for three families of local planner.

TEB’s authors ran one differential-drive robot (speed −0.2 to 0.4 m/s, turn rate at most 0.4 rad/s) to three goals in a 10 m by 10 m map in ROS, with the global plan refreshed every 2 s and every local planner at 10 Hz (Rösmann et al. 2021, §IV-B). Figure 16 shows their Table I.

In our room the same ranking holds for the drive: TEB passes the person without a new global plan and satisfies Nav2’s default test at 8.3 s, while DWB needs the plan remade and takes 13.3 s (Section 10).
