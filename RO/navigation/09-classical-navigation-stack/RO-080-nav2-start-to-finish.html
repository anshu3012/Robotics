1. Overview

Key point

Nav2 drives a robot to a goal pose with 17 separate programs, most of them servers with one job each: a lifecycle manager starts them in order, AMCL says where the robot is, two costmaps say where it may go, a behaviour tree asks the planner for a path and the controller for commands, and a velocity smoother and a collision monitor check each command before it reaches the wheels. In our own Python version of these servers, run on the room, one goal crosses all of them and the robot reaches the door in 11.50 s, replanning once round the person.

Every part of a navigation stack has been built in this course, one at a time:

  • a global path on a grid, by Dijkstra’s algorithm ()Dijkstra’s algorithm: A search that always settles the vertex with the smallest distance from the start found so far, which is then final, and offers each of its neighbours the route through it, keeping the shorter; with every edge cost at least 0 it finds the shortest route to every vertex (3.414 m to the door on the room grid with diagonals). Explained in: Dijkstra’s Algorithm and Priority Queues, §3.2 The algorithm: settle the nearest, update its neighbours and A* ()A search:* Dijkstra’s algorithm with the open list sorted by f=g+h, the cost so far plus a heuristic guess of the cost left; with a consistent heuristic it returns the shortest route while expanding far fewer states (9 cells against 54 on the room grid). Explained in: A* and Heuristics, §4.5 The algorithm;
  • where the robot is, by a particle filter ()Particle filter: A Bayes filter that stores the belief as a set of weighted samples (particles) and runs each round as move, weigh, resample; it can hold beliefs of any shape, such as a belief with three modes, one at each of three doors. Explained in: Particle Filter, §4. The particle filter, step by step on a map;
  • the commands round a person, by the local planners DWB ()DWB controller: Nav2’s controller that, 20 times a second by default, samples speed and turn-rate commands within the acceleration limits, rolls each out, scores the rollouts with plug-in critics and sends the lowest; the successor of ROS 1’s DWA, it follows the global plan and cannot search round an obstacle on its own. Explained in: Behaviour Trees and Recovery: Deciding What the Robot Does Next, §3. Behaviour trees: a tick and three answers;
  • and the communication between programs, by the nodes, topics and actions of ROS 2 ()ROS 2 (Robot Operating System 2): An open-source set of libraries and tools that runs a robot’s software as separate programs (nodes) passing typed messages over topics, services and actions, and that configures, starts, records and shows them; it lets parts written by different people work together at their own rates. Explained in: ROS 2: Nodes, Topics, Services and Actions, §2.1 One program per job: nodes.

What is still missing is the complete system: which program runs each part, in what order they start, what each one sends to which, and how a goal selected on a map becomes wheel speeds. 2. Bring-up: launch files and the lifecycle manager

Key point

Before the first goal, 17 managed nodes must exist, have read their parameters and be ready, in an order in which each node’s inputs come first. One lifecycle manager configures all 17 in order, then activates all 17 in order, and keeps a heartbeat with each, so that the failure of one node stops all of them.

2.1 Why the start-up needs an order

The goal of the Overview needs the map before AMCL can localise on it, and AMCL’s position before any costmap can place a scan on the map. If the 17 programs started at once, a server could receive its first message before the server it depends on exists, and the goal would fail unpredictably. ROS 2’s lifecycle nodes ()Lifecycle node (managed node): A node with the states Unconfigured, Inactive, Active and Finalized that it changes only when another program requests a transition (configure, activate, deactivate, cleanup, shutdown); a manager can then set nodes up and start them in order, and restart or replace them while the system runs. Explained in: ROS 2: Nodes, Topics, Services and Actions, §9. Lifecycle nodes: starting in the right order, nodes that change state (unconfigured, inactive, active) only when told, make the order controllable, provided that one node issues the transitions.

2.2 The launch files

Nav2’s bring-up is five launch files ()Launch file: A file, in Python, XML or YAML, that lists the nodes to start with their parameters, names and arguments, and that ros2 launch runs as a whole; one command starts the whole stack and one Ctrl+C stops it, and launch files can include others. Explained in: ROS 2: Nodes, Topics, Services and Actions, §8. Launch files: the whole stack in one command in nav2_bringup/launch (branch main), shown as an example of nested launch files in ROS 2 in Nav2Explained in: ROS 2: Nodes, Topics, Services and Actions, §10. ROS 2 in Nav2, Autoware and Apollo; for our goal, the order they set is what matters:

  • localization_launch.py starts map_server and amcl;
  • keepout_zone_launch.py and speed_zone_launch.py, both on by default (use_keepout_zones, use_speed_zones), each start two servers for a costmap filter: a mask server and a filter-info server;
  • navigation_launch.py starts the eleven navigation servers, from controller_server to following_server; Figure 1 lists them in their order;
  • bringup_launch.py includes the other four launch files and starts one lifecycle manager, named lifecycle_manager_nav2; the manager’s parameter node_names lists the localisation nodes, then the four filter servers, then the navigation servers: 17 nodes.

A costmap filter reads a mask, a second map that marks areas the robot must keep out of or must cross slowly. Our room has no such areas, so the filter servers start but our run leaves the filters out.

The launch files also rename topics so that the commands pass through two checks: controller_server and behavior_server publish on cmd_vel_nav instead of cmd_vel, velocity_smoother turns cmd_vel_nav into cmd_vel_smoothed, and collision_monitor turns cmd_vel_smoothed into the cmd_vel the base obeys (bring-up nav2_params.yaml, cmd_vel_in_topic and cmd_vel_out_topic).

2.3 The lifecycle manager

The node that moves a list of lifecycle nodes through their states in a fixed order, and watches them afterwards, is the lifecycle manager ()Lifecycle manager (Nav2): The node that configures a list of lifecycle nodes in order, then activates them in order, and keeps a heartbeat (bond) with each; it guarantees every server is ready before the first goal and brings the system down if one fails. Explained in §2.3 The lifecycle manager. (lifecycle_manager.cpp; Macenski et al. 2023 §IX). Its startup() does two passes:

  1. configure every node in list order: each reads its parameters and creates its publishers, services and action servers;
  2. activate every node in list order: each starts publishing and accepting goals.

Shutting down runs the same transitions backwards, from the last node to the first. Figure 1 plays the start-up. Watch the column of states: every node becomes inactive (orange) before any becomes active (green), and map_server leads both passes.

After the second pass the manager starts a bond with each node: every node sends a heartbeat every 0.25 s, the manager checks every 0.2 s, and a node silent for 4 s is taken as failed, which brings the system down (lifecycle_manager.cpp: bond_heartbeat_period 0.25, bond_timeout 4.0, a 200 ms timer). In all, 17 nodes and 34 transitions (notebook). The servers are now ready, and a goal can arrive.

4. Where the robot is: the map server and AMCL

Key point

AMCL is the particle filter on the map, with a likelihood field for the laser; it publishes the correction from the odometry frame to the map frame. In our run odometry drifts 0.222 m by the end, and AMCL keeps the estimate within 0.054 m, with odometry noise settings that match our robot.

4.1 The map, and why odometry is not enough

Every server of Figure 2 needs the robot’s place on the map: the planner to start the path, the controller to compare the robot with the path. Odometry gives a place, but it drifts. Our robot’s left wheel is 1 percent smaller than its wheel odometry ()Wheel odometry: Working out a robot’s pose by adding up the wheel motion its encoders measure: ticks to wheel distances, to the robot’s move and turn, to a new pose; accurate over short distances but it drifts, because every error stays in the sum. Explained in: Probabilistic Motion Models: Velocity and Odometry, §3.1 From encoder ticks to a new pose assumes, so by the end of the drive odometry puts the robot 0.222 m and 9.3° away from where it is (notebook).

The map comes from the map server ()Map server: The Nav2 node that loads a saved occupancy grid map and serves it on the /map topic, so AMCL and the global costmap work on the same map. Explained in §4.1 The map, and why odometry is not enough., the node that loads a saved occupancy grid ()Occupancy grid: A grid map that stores in each cell a number between 0 and 1, such as the probability that the cell is occupied, instead of a hard 0 or 1; the standard grid map of robotics, since sensor readings are uncertain. Explained in: Maps and Landmarks, §5.2 Bitmaps and occupancy grids and serves it on the /map topic. Ours is the room in 0.05 m cells, 160 by 100 cells reaching 0.5 m beyond the walls, as a map recorded by driving through the room would.

4.2 AMCL

Nav2’s localiser is AMCL ()AMCL (adaptive Monte Carlo localisation): Nav2’s localiser: a particle filter on a known map that moves its particles with odometry, weights them with a laser likelihood field and adapts their number; it publishes the map-to-odometry transform that corrects odometry’s drift. Explained in §4.2 AMCL., adaptive Monte Carlo localisation: a particle filter ()Particle filter: A Bayes filter that stores the belief as a set of weighted samples (particles) and runs each round as move, weigh, resample; it can hold beliefs of any shape, such as a belief with three modes, one at each of three doors. Explained in: Particle Filter, §4. The particle filter, step by step whose particles are poses on the map, moved with the odometry motion model ()Odometry motion model: A motion model that splits the pose change reported by odometry into a first turn, a straight drive and a second turn, and adds independent noise to each, with a standard deviation that grows with the motion; used when wheel encoders exist. Explained in: Probabilistic Motion Models: Velocity and Odometry, §4. The odometry motion model and weighted by the laser with the likelihood field model ()Likelihood field model: A measurement model for range finders that scores each reading by how close its beam endpoint lands to an obstacle in the map (a Gaussian of that distance plus a small uniform part prand​, so no reading scores 0); it is fast and smooth because it skips ray casting, but it ignores what lies along the beam. Explained in: Likelihood Fields and Scan Matching, §3.2 From distance to density, with a particle count that adapts to how spread out the particles are (Nav2 docs, “State Estimation”; nav2_amcl). Monte Carlo localisation is this particle filter run on a known map, each particle a guess of the pose; here we follow Nav2’s version of it.

AMCL updates its particles only after the odometry has moved 0.25 m or turned 0.2 rad (update_min_d, update_min_a), and then:

  1. moves every particle by the odometry change, with noise (DifferentialMotionModel);
  2. scores every particle with 60 of the laser’s beams against the map (max_beams);
  3. resamples, keeping between 500 and 2000 particles (min_particles, max_particles), fewer when they are concentrated in a small region.

The score of one beam. With:

  • z is the distance from where the beam ends, seen from the particle, to the nearest occupied cell of the map, in m, at most 2.0 m (laser_likelihood_max_dist);
  • σ is the laser’s noise, 0.2 m (sigma_hit);
  • zhit​ and zrand​ are the weights of a true hit and of a random reading, 0.5 each in the bring-up file;
  • rmax​ is the laser’s range, 30 m;
  • pz​ is the beam’s score, a number between 0 and 1.

A beam that ends on a wall, z=0:

pz​=0.5+0.5/30=0.5167

A beam that ends 0.4 m from any wall:

pz​=0.5×e−0.42/(2×0.22)+0.0167 =0.5×e−2+0.0167=0.0843

The same score in symbols:

pz​=zhit​e−z2/2σ2+rmax​zrand​​

The Gaussian term is the likelihood field’s density of a hit near a wall; the constant term prevents one reading from an obstacle the map lacks, such as the person, from reducing a good particle’s score to almost zero. Nav2’s code then adds the cubes of the 60 beam scores to 1 to weight the particle (likelihood_field_model.cpp): a wall hit adds 0.1379, a beam 0.4 m off adds 0.0006 (notebook).

4.3 The correction AMCL publishes

AMCL does not move the robot’s odometry. AMCL publishes the transform from the map frame to the odometry frame, chosen so that the odometry pose, carried by that transform, lands on AMCL’s estimate; every server then looks up the robot’s place on the map through it (Nav2 docs, “State Estimation”). The three frames are those of the transform tree: map is fixed to the room, odom is where odometry started counting, and base_link moves with the robot.

A setting that must match the robot. The four alpha values say how noisy AMCL should assume odometry is. The bring-up file’s 0.2 suits a robot with poor odometry; ours is reliable apart from its 1 percent wheel, so we use 0.005, the value the ROS Navigation Tuning Guide uses for reliable odometry, noting that “when the odometry model is less noisy, the particles are more condensed” (Zheng §5.2). With the file’s 0.2 the same run spreads the particles (1471 at the end), and the estimate is up to 0.447 m off, 0.212 m on average (notebook). AMCL’s estimate now stays within about 5 cm of the true pose; the next question is where the robot may drive.

5. Where the robot may go: the global and local costmaps

Key point

Both costmaps stack layers on a grid: the map’s walls (global only), what the laser sees, and an inflated cost round every obstacle cell, 253 within the robot’s radius and falling to 65 at 0.70 m. The global costmap covers the room for the planner and updates once a second; the local one covers 3 m by 3 m round the robot for the controller and updates five times a second.

5.1 Why two costmaps, built from layers

The map of Section 4 has no person, and it marks walls as thin lines of cells that a robot of radius 0.25 m must keep its centre 0.25 m away from. The three layers, as the bring-up file sets them (nav2_params.yaml; plug-ins of nav2_costmap_2d):

  1. static layer (StaticLayer): the map’s occupied cells become 254;
  2. obstacle layer (ObstacleLayer): each scan clears the cells its beams cross, up to 3.0 m (raytrace_max_range), then marks the cells where beams end within 2.5 m (obstacle_max_range); a mark stays until a later beam passes through it;
  3. inflation layer (InflationLayer): every cell gets a cost from its distance to the nearest cell of cost 254.

5.2 The inflation cost

The inflation layer uses the rule of the costmap the critics readExplained in: DWA and Nav2’s DWB Controller, Start to Finish, §5.1 The costmap the critics read: 254 on an obstacle cell, 253 within the robot’s radius because a robot centred there would overlap the obstacle, then falling exponentially with distance out to inflation_radius, 0.70 m, at the rate cost_scaling_factor, 3.0 per metre. For a cell 0.30 m from an obstacle, 0.05 m beyond our robot’s radius of 0.25 m:

252×e−3.0×(0.30−0.25)=216.9

which the code cuts to the whole number 216. The falling costs make the planner prefer cells farther from obstacles: 216 at 0.30 m, 119 at 0.50 m and 65 at 0.70 m (notebook).

5.3 Global and local

The global costmap ()Global costmap: The costmap the planner uses: the whole map in the map frame, with static, obstacle and inflation layers, updated about once a second; it tells the planner where the robot’s centre may go. Explained in §5.3 Global and local. is the one the planner uses: it covers the whole map in the map frame, with all three layers, updated once a second (update_frequency 1.0). The local costmap ()Local costmap: The costmap the controller uses: a small rolling window centred on the robot (3 m by 3 m in Nav2’s bring-up) in the odometry frame, built from the sensors and inflated, updated several times a second so new obstacles appear quickly. Explained in §5.3 Global and local. is the one the controller uses: a rolling window of 3 m by 3 m centred on the robot in the odometry frame, with the obstacle and inflation layers only, updated five times a second (update_frequency 5.0, rolling_window true). 6.1 The behaviour tree navigator

The goal of the Overview arrives as a NavigateToPose action at the BT navigator ()BT navigator: Nav2’s server that receives a navigation goal as an action and ticks a behaviour tree, by default every 10 ms, whose nodes call the planner, controller and behaviour servers; changing the tree’s XML file changes how the robot navigates. 6.2 The planner server and NavFn

The planner server ()Planner server: Nav2’s server that answers path requests (ComputePathToPose) with a planner plug-in such as NavFn, on the global costmap it hosts, and checks whether a path is still free (IsPathValid). Explained in §6.2 The planner server and NavFn., planner_server, answers ComputePathToPose with the plug-in named in the request, on its global costmap (Nav2 docs, “Navigation Servers”). The bring-up’s plug-in, GridBased, is NavFn ()NavFn: Nav2’s default global planner: it gives each costmap cell a traversal cost 50+0.8c, spreads a potential from the robot’s cell like a wave (Dijkstra’s order, or A*‘s), and follows the potential’s slope from the goal in half-cell steps to make the path. Explained in §6.2 The planner server and NavFn. (nav2_navfn_planner) with use_astar false, so it spreads costs like Dijkstra’s algorithm ()Dijkstra’s algorithm: A search that always settles the vertex with the smallest distance from the start found so far, which is then final, and offers each of its neighbours the route through it, keeping the shorter; with every edge cost at least 0 it finds the shortest route to every vertex (3.414 m to the door on the room grid with diagonals). Explained in: Dijkstra’s Algorithm and Priority Queues, §3.2 The algorithm: settle the nearest, update its neighbours rather than A* ()A search:* Dijkstra’s algorithm with the open list sorted by f=g+h, the cost so far plus a heuristic guess of the cost left; with a consistent heuristic it returns the shortest route while expanding far fewer states (9 cells against 54 on the room grid). Explained in: A* and Heuristics, §4.5 The algorithm. NavFn works in three steps (navfn.cpp):

  1. turn each costmap cell into a traversal cost, so that a free cell still costs something and an inflated one costs more;
  2. spread a potential, the cheapest cost to reach each cell, outwards from the robot’s cell, like a wave whose front cuts across cells instead of following grid lines (the planar-wave update, the idea of the fast marching method ())Fast marching method: Dijkstra’s loop run on a grid with an update that takes a cell’s arrival time from two neighbours at once, one across and one up or down, so a front spreading from the goal can cross the grid at any angle; its distances get closer to the true ones as the cells shrink, unlike 8-connected Dijkstra’s. Explained in: Grid Path Planning: Wavefronts, Navigation Functions and Value Iteration, §7.2 Fast marching;
  3. walk from the goal down the potential’s slope in steps of half a cell, and reverse the walk into the path.

The traversal cost. With:

  • c is the costmap cost of a cell, from 0 to 252;
  • h is NavFn’s traversal cost for the cell.

A cell of costmap cost 216, 0.30 m from an obstacle:

h=50+0.8×216=222.8

The same rule in symbols:

h=50+0.8c

So the cell costs 4.46 times a free cell, which costs 50. Cells of cost 253 and 254 get 254, which the wave never enters. The 50 for a free cell makes the potential grow with distance even in open space, and the factor 0.8 spreads the costs 0 to 252 evenly over the range from 50 to about 252, which keeps paths in the middle of a passage (the NavFn source’s comment, quoted in Zheng §2.2).

Our two plans (notebook, Figure 4, frame 4):

  • at 0.0 s, 3.26 m and 130 poses, from the robot to the door, through where the person will stand;
  • at 3.0 s, 2.986 m, from where the robot then was, round the person’s left; NavFn’s wave reached 7358 of the 16000 cells.

The plan at 0 s is shorter than the 3.414 m of A* on 0.5 m cellsExplained in: A* and Heuristics, §4.5 The algorithm, because NavFn’s 0.05 m cells and its wave cut corners that 0.5 m cells could not. A path is not yet a command; the controller server turns it into commands.

7. The controller server

Key point

The controller server runs 20 times a second: it puts the path in the odometry frame, keeps the part ahead of the robot, checks whether the goal is reached or progress has stopped, and asks its plug-in for a command. Our run uses DWB, the controller Nav2’s documentation calls the default; the bring-up file itself names MPPI.

7.1 One controller cycle

The path of Section 6 is in the map frame, but the local costmap is in the odometry frame and moves with the robot. The controller server ()Controller server: Nav2’s server that follows a path (FollowPath): 20 times a second by default it transforms the path into the odometry frame, keeps the part ahead, checks goal and progress, and asks a controller plug-in such as DWB or MPPI for a velocity command. Explained in §7.1 One controller cycle., controller_server, bridges them in each cycle, 20 times a second (controller_frequency 20.0) (nav2_controller/src/controller_server.cpp):

  1. transform the path into the odometry frame with AMCL’s correction;
  2. keep the part from the pose nearest the robot to 2.0 m ahead, and inside the local costmap (FeasiblePathHandler, prune_distance);
  3. check the goal: within 0.25 m, then within 0.25 rad of its heading (SimpleGoalChecker, stateful);
  4. check progress: the robot must move 0.5 m every 10 s (SimpleProgressChecker);
  5. ask the plug-in FollowPath for a command and publish it on cmd_vel_nav.

The goal checker and progress checkerGoal checker: The test a controller runs to decide that the robot has reached its goal, such as Nav2’s default: the position within 0.25 m, then the heading within 0.25 rad, with the position kept as reached while the robot turns; it ends the path-following action with success. Explained in: Behaviour Trees and Recovery: Deciding What the Robot Does Next, §8. The goal checker and the progress checker are taught with recovery behaviours. Steps 1 to 4 and our plug-in, DWB, come from the Python version of the controller server written for DWA and DWBExplained in: DWA and Nav2’s DWB Controller, Start to Finish, §6. One cycle start to finish, in the order the code runs.

7.2 DWB in our run

DWB ()DWB controller: Nav2’s controller that, 20 times a second by default, samples speed and turn-rate commands within the acceleration limits, rolls each out, scores the rollouts with plug-in critics and sends the lowest; the successor of ROS 1’s DWA, it follows the global plan and cannot search round an obstacle on its own. What goes in and what comes out samples speed and turn-rate pairs the robot can reach, rolls each out for 1.7 s, scores the rollouts with its critics and keeps the cheapest.   • the window of speeds is 0 to 0.6 m/s and of turn rates −1 to 1 rad/s;

8. After the controller: the velocity smoother and the collision monitor

Key point

The velocity smoother limits how fast each command may change, 20 times a second; the collision monitor then checks the smoothed command against the raw scan, outside every planner, and scales it by the time to collision over 1.2 s. In our run the smoother turns DWB’s first 0.4737 m/s into 0.025 m/s, and the monitor acts once, at 2.55 s, scaling the command by 0.917.

8.1 The velocity smoother

DWB’s first command, at 0.0 s, is 0.4737 m/s and 0.6842 rad/s, while the robot is at rest. A base given that command would change its speed in one step, far beyond its acceleration limit. The velocity smoother ()Velocity smoother: A node between the planner and the robot’s base that clamps each velocity command to the speed limits, limits its rate of change and applies a deadband, such as Nav2’s nav2_velocity_smoother; it turns abruptly changing planner output into commands the drive can follow. Explained in: Feedforward, Integral Action, Cascaded Loops and Windup, §7.2 Deadband: dropping commands too small for the motors, velocity_smoother, runs 20 times a second (smoothing_frequency 20.0) and, in open loop (feedback: OPEN_LOOP), changes its last output towards the new command by at most the acceleration limit over one period (velocity_smoother.cpp, applyConstraints). With:

  • v and ω are the smoother’s last output speed and turn rate, in m/s and rad/s, both 0 before the first command;
  • vnew​ and ωnew​ are its next output, in m/s and rad/s, moved towards DWB’s command;
  • a is the speed’s acceleration limit, 0.5 m/s² for our robot, and α the turn rate’s, 3.2 rad/s²;
  • f is the smoothing frequency, 20 Hz.

The first output, from rest:

vnew​=0+0.5/20=0.025 m/s ωnew​=0+3.2/20=0.16 rad/s

In symbols, each period the output moves towards DWB’s command by at most:

∣vnew​−v∣≤a/f ∣ωnew​−ω∣≤α/f

At 1.0 s, DWB asks for 0.5684 m/s and the smoother gives 0.525 m/s, its last output of 0.5 m/s plus 0.025 (notebook). The smoothed command goes out on cmd_vel_smoothed.

8.2 The collision monitor

The costmaps of Section 5 update at 1 Hz and 5 Hz, and DWB plans on what they held at their last update. The collision monitor ()Collision monitor: Nav2’s node between the velocity smoother and the robot base that checks each velocity command against raw sensor returns in zones round the robot and stops, slows or limits it, independently of the planners and costmaps. Explained in §8.2 The collision monitor., collision_monitor, is a last check that works on the raw scan at every command: it looks for scan returns inside zones round the robot and slows or stops the command, “bypassing navigation’s planners” (Macenski et al. 2023 §IX; nav2_collision_monitor README). The bring-up file enables one zone, FootprintApproach.

The approach zone works on time (polygon.cpp, getCollisionTime):

  1. move the robot’s footprint (16 points on a circle of the robot’s radius) forward with the command, 0.1 s at a time (simulation_time_step), up to 1.2 s (time_before_collision);
  2. at the first step whose footprint holds 6 or more scan returns (min_points), take the loop’s time at that step as the time to collision;
  3. scale the command by the time to collision over 1.2 s.

Keeping the robot that many seconds from any collision is the approach zone ()Approach zone (collision monitor): The collision monitor’s model that moves the robot’s footprint forward with the command in short steps and, if returns enter it within a set time (1.2 s in Nav2’s bring-up), scales the command by the time to collision over that time, so the robot always stays that long from a collision. Explained in §8.2 The collision monitor. (nav2_collision_monitor README: “keep the robot always M seconds from any collision”).

8.3 Stop, slowdown and limit zones

The approach zone is one of four kinds. The example parameter file of the package nav2_collision_monitor, named collision_monitor_params.yaml, defines all of them; zones of the first three kinds act on returns inside a fixed polygon:

  • stop: 4 or more returns in a box 0.3 m ahead of the robot’s centre and 0.6 m wide set the command to 0;
  • slowdown: returns in a box 0.8 m by 0.8 m multiply the command by 0.3;
  • limit: returns in a box 1.0 m by 1.0 m cap the speed at 0.4 m/s and the turn rate at 0.5 rad/s;
  • approach: as above, here with 2.0 s.

Each zone’s polygon, its action and its number of returns make a collision zone ()Collision zone (stop, slowdown, limit): A polygon round the robot with an action and a minimum number of sensor returns: enough returns inside it stop the robot, multiply its command by a ratio, or cap its speed and turn rate; zones must be sized to the robot’s own footprint. Explained in §8.3 Stop, slowdown and limit zones. (nav2_collision_monitor README). With several zones, the monitor checks them in order and keeps the safest command, smallest in speed and turn rate together; a stop ends the checks (collision_monitor_node.cpp, process).
